# 역할 추천 합성 점검 (#136)

`run.py`는 **가상의 작업·팀원 데이터만** GMS에 보내는 유료 호출이다. 호출하기
전 키와 모델 사용 권한이 필요하다. `ai/`에서 다음을 실행한다.

```text
python -m evaluations.assignment_recommendations.run --env-file <설정파일경로>
```

담당 영역, 업무량, 선행 작업 담당자, 업무량 미제공의 네 사례를 각각 한 번 호출한다.
각 사례의 `expected_for_fixture`는 이 합성 사례를 검토하기 위한 예상 후보일 뿐
조직의 인사 기준이나 최적 배정의 정답이 아니다. 응답에 선택된 후보·대안·서버가
생성한 이유·미확인 정보·실제 usage를 기록한다. 실행 결과는 모델마다 달라질 수
있으며, 소수 합성 사례의 통과가 실제 사용자나 공정성·배정 품질을 보장하지 않는다.

## 2026-11-06 실제 GMS 점검

후보별 기준 형식으로 `gpt-6-luna`에 네 사례를 두 차례씩 보냈다. 두 차례 모두
담당 영역은 21, 업무량은 22, 선행 작업은 22, 업무량 미제공은 21을 우선 후보로
반환해 합성 사례의 예상과 같았다. 모두 대안과 usage가 있었고, 업무량 미제공
사례는 0건으로 단정하지 않았다. 최종 출력 상한 4096인 두 번째 실행의 입력/출력
토큰은 순서대로 639/174, 637/145, 662/179, 637/220이었다.

업무량 사례에서 두 후보의 담당 영역은 같고 관측 업무는 3건과 0건이었지만 모델은
첫 실행에서는 두 후보의 주요 기준을 모두 `AREA`로, 두 번째는 `WORKLOAD`로 반환했다.
서버가 각 업무 건수는 정확히 표시해도 모델이 순위를 정한 실제 이유를 검증하지는
못한다. 이 결과는 여덟 번의 합성 호출에
한정되며, 이 평가만으로 실제 팀 데이터에 대한 추천 품질을 확인할 수 없다.

추가로 같은 날짜에 합성 입력을 FastAPI `TestClient`의 내부 HTTP 경로에서 실제
GMS에 한 번 보냈다. HTTP 200, 모델 결과와 이유·대안, 성공한 `TASK_ASSIGNMENT`
usage를 확인했다. 이는 프로세스 안의 HTTP 경로 시험이며 실제 BE·FE 서버 연결은 아니다.

## 2026-11-06 실제 서버 연동 점검

격리된 로컬 PostgreSQL에 가상 계정 두 명, 선행 작업과 추천 대상 작업을 만들고
FastAPI·Spring Boot·Vite를 각각 실행했다. AI 경로를 로컬에서만 켠 뒤 실제 GMS를
연결했다. BE API 직접 호출과 Chrome 작업 화면의 추천 요청이 각각 HTTP 200과
`origin=MODEL`, 우선 후보·대안의 이유를 반환했다. 브라우저에 두 이유가 표시되고
작업 두 건의 담당자·상태·잠금 번호는 변하지 않았으며 사용량 기록도 확인했다.
실제 BE에서 미인증 401, 비멤버 404, 없는 작업 404, 허용되지 않은 Origin 403을
확인했다. 모델 호출 중 멤버가 바뀌는 경우는 실제 Postgres와 AI 대역을 쓰는 BE 통합
테스트에서 409로 검증했다. 이 결과는 가상 데이터에 한정되며 추천 품질 보증은 아니다.
