# fe-feature

코드 패턴(`useMe`, `LoginForm`, 테스트 예제)은 `frontend/README.md`의 "코드 컨벤션"에 있다. 이 스킬은 순서와 판단 기준만 다룬다.

## 0. 시작 전

1. 요구사항을 두세 문장으로 정리해 사용자에게 확인한다. 어떤 화면인지, 사용자가 무엇을 하는지, 성공과 실패 때 무엇이 보이는지를 적는다.
2. Jira 티켓 키를 확인한다. 현재 브랜치가 `<타입>/frontend-<기능>-<키>` 형식이 아니면 사용자에게 알린다.
3. `docs/decisions.md`에서 관련 결정을 확인한다.

애매한 부분이 있으면 여기서 묻는다. 추측으로 만들고 나중에 고치지 않는다.

## 1. 위치 정하기

- 도메인 이름을 정하고 `src/features/<도메인>/`에 둔다. 그 기능에서만 쓰는 컴포넌트, 훅, 스키마, store는 모두 이 폴더에 넣는다.
- 라우트가 필요하면 화면은 `src/pages/XxxPage.tsx`에 둔다.
- 두 곳 이상에서 쓰게 될 때만 `components/`, `stores/`, `lib/`로 옮긴다.

## 2. 데이터

- API가 있으면 `fe-api` 스킬 절차로 스키마와 query/mutation 훅을 먼저 만든다.
- 서버 데이터는 TanStack Query로만 관리한다. 여러 컴포넌트가 공유하는 화면 상태만 Zustand에 두고, 나머지는 `useState`로 처리한다.

## 3. 화면

- 필요한 UI 요소가 `src/components/ui/`에 있는지 먼저 본다. 없고 shadcn에 있으면 `npx shadcn add <이름>`으로 추가한다.
- 폼은 React Hook Form + `zodResolver`로 만들고 검증 규칙은 스키마에만 쓴다.
- 로딩, 에러, 데이터 없음 상태를 모두 화면에 처리한다.
- 접근성 기본을 지킨다. 입력에는 label, 아이콘 버튼에는 `aria-label`, 이미지에는 `alt`를 단다.
- 화면 문구는 한국어로 쓴다.
- 3D가 들어가면 `three-scene` 스킬을 따른다.

## 4. 라우트

- `src/router.tsx`에 추가한다.
- 3D나 큰 라이브러리를 쓰는 화면, 첫 화면에 필요 없는 화면은 route `lazy`로 분리한다.

## 5. 테스트

| 대상                     | 테스트                                           | 위치                   |
| ------------------------ | ------------------------------------------------ | ---------------------- |
| 스키마, 변환 함수, store | Vitest 단위 테스트                               | 대상 옆 `*.test.ts`    |
| 폼, 입력 컴포넌트        | RTL (`getByRole`, `getByLabelText`, `userEvent`) | 대상 옆 `*.test.tsx`   |
| 새 페이지, 라우트        | Playwright (API는 `page.route`로 대체)           | `e2e/<도메인>.spec.ts` |

테스트 이름은 "무엇을 하면 어떻게 된다"처럼 한국어로 쓴다. 실패하면 코드를 고친다. 테스트를 지우거나 `skip`하거나 기대값을 바꿔서 통과시키지 않는다.

## 6. 마무리

1. `npm run format`을 실행한다.
2. `fe-verify`로 검증한다.
3. 스택이나 구조가 바뀌었으면 README를, 결정이 생겼으면 `docs/decisions.md`를 고친다.
4. 바뀐 파일 목록, 검증 결과, 확인하지 못한 것을 보고한다. 커밋은 요청받았을 때만 `fe-commit-pr`로 한다.
