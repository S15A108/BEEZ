# 프론트엔드 결정 기록

프론트에서 무엇을 왜 골랐고 왜 뺐는지 남기는 문서입니다. 같은 논의를 다시 하지 않도록, 도구나 구조를 바꾸기 전에 여기를 먼저 확인합니다.

기록 규칙은 세 가지입니다.

- 새 결정은 맨 아래에 번호를 이어서 추가합니다.
- 결정이 바뀌어도 기존 항목은 지우지 않습니다. 제목 앞에 `[대체됨 → D번호]`를 붙이고 새 항목을 추가합니다.
- "다시 볼 조건"이 생기면 그 항목부터 다시 검토합니다.

## D1. 프론트는 `frontend/` 안에서만 관리한다

- **날짜**: 2026-10-19
- **결정**: 프론트는 `frontend/`에 독립된 앱으로 두고 자체 `package.json`, lockfile, 설정 파일을 가집니다. 레포 루트 파일은 수정하지 않습니다.
- **이유**: 레포 루트와 팀 공용 설정(`docs/`, `.github/`, 루트 `.gitignore` 등)은 팀장이 관리합니다. 루트에 `package.json`이 없으면 백엔드와 AI 팀원이 Node 없이 작업할 수 있습니다.
- **검토한 대안**: Turborepo, Nx, pnpm workspace. JS 패키지만 관리하는 도구라 JS 앱이 하나인 지금은 필요 없습니다.
- **다시 볼 조건**: JS 앱이나 공유 TS 패키지가 두 개 이상 생길 때

## D2. Vite + React + TypeScript로 만든다

- **날짜**: 2026-10-19
- **결정**: 빌드 도구는 Vite, UI는 React, 언어는 TypeScript(strict)입니다.
- **이유**: SSR이나 SEO가 필요 없습니다. 빌드 결과가 정적 파일이라 배포가 단순합니다.
- **검토한 대안**: Next.js. Node 서버가 하나 더 필요하고 배포 구성이 복잡해집니다.
- **다시 볼 조건**: 검색 노출이나 서버 렌더링이 요구사항에 들어올 때

## D3. 패키지 매니저는 npm, Node는 24로 고정한다

- **날짜**: 2026-10-19
- **결정**: npm을 쓰고 lockfile을 커밋하며, 설치는 `npm ci`로 합니다. `engines`(`>=24 <25`)와 `.npmrc`의 `engine-strict=true`로 다른 Node 버전에서는 설치가 실패하게 합니다.
- **이유**: npm은 Node에 포함되어 있어 따로 설치할 것이 없습니다. 팀원마다 Node 버전이 다르면 lockfile이 계속 바뀝니다.
- **검토한 대안**: pnpm. 더 빠르지만 팀원 PC와 CI에 corepack 설정이 추가됩니다.

## D4. Lint는 Oxlint 대신 ESLint를 쓴다

- **날짜**: 2026-10-19
- **결정**: ESLint + typescript-eslint + react-hooks + react-refresh를 씁니다. Vite 공식 템플릿(`--eslint`) 설정을 그대로 가져왔습니다.
- **이유**: 팀원 대부분이 써 봤고 자료가 많으며 플러그인을 모두 쓸 수 있습니다. 이 규모 프로젝트에서는 속도 차이가 크지 않습니다.
- **검토한 대안**: Oxlint(create-vite 9의 기본값). 빠르지만 일부 플러그인이 없습니다.
- **참고**: shadcn 컴포넌트는 variants를 컴포넌트와 같이 export하므로 `src/components/ui/`에서만 `react-refresh/only-export-components`를 끕니다.

## D5. 포매터는 Prettier, 작은따옴표에 세미콜론 없음

- **날짜**: 2026-10-19
- **결정**: Prettier에 `semi: false`, `singleQuote: true`, Tailwind 클래스 정렬 플러그인을 씁니다. `package-lock.json`은 포맷 대상에서 뺍니다.
- **이유**: Vite 템플릿 스타일과 같아서 기존 파일이 가장 적게 바뀝니다. lockfile을 Prettier가 고치면 npm이 다시 되돌려서 diff가 계속 생깁니다.
- **참고**: `eslint-config-prettier`는 넣지 않았습니다. 지금 ESLint 추천 설정에는 Prettier와 충돌하는 포맷 규칙이 없습니다.

## D6. 스타일링은 Tailwind CSS, UI 컴포넌트는 shadcn/ui

- **날짜**: 2026-10-19
- **결정**: 스타일은 Tailwind 유틸리티 클래스로 씁니다. 버튼, 입력, 다이얼로그 같은 UI는 shadcn/ui(Radix, nova 프리셋)에서 필요한 것만 `npx shadcn add`로 가져옵니다.
- **이유**: 간격과 색상이 정해진 값 안에서만 쓰여 팀원마다 스타일이 갈라지지 않습니다. shadcn은 소스가 레포에 복사되어 AI가 읽고 고칠 수 있고, AI가 화면마다 다른 컴포넌트를 새로 만들지 않고 같은 컴포넌트를 재사용합니다.
- **검토한 대안**: CSS Modules. 의존성이 없지만 공통 값을 따로 관리해야 하고 작성 방식이 사람마다 달라집니다.
- **다시 볼 조건**: 디자인 시스템이 정해지면 테마 토큰(색, radius)과 한글 폰트를 바꿉니다. 기본 폰트 Geist에는 한글이 없습니다.

## D7. 상태와 API 호출은 TanStack Query, Zustand, axios로 나눈다

- **날짜**: 2026-10-19
- **결정**: 서버에서 받은 데이터는 TanStack Query로만 관리합니다. 서버와 상관없는 화면 상태 중 여러 컴포넌트가 공유하는 것만 Zustand에 둡니다. API 요청은 `src/api/client.ts`의 axios 인스턴스(`baseURL: /api`) 하나로만 보냅니다.
- **이유**: 캐싱, 로딩, 에러, 재요청을 직접 구현하지 않아도 됩니다. 인증 헤더나 공통 에러 처리를 고칠 곳이 한 군데로 모입니다.
- **검토한 대안**: fetch 래퍼. 의존성은 없지만 interceptor와 타임아웃을 직접 만들어야 합니다.

## D8. 라우팅은 React Router의 `createBrowserRouter`

- **날짜**: 2026-10-19
- **결정**: React Router 8의 data router(`createBrowserRouter` + `RouterProvider`)를 쓰고, 라우트는 `src/router.tsx` 한 곳에 정의합니다. 무거운 페이지는 route `lazy`로 분리합니다.
- **이유**: route 단위 코드 분할이 기본으로 됩니다. 3D 페이지처럼 큰 화면을 첫 번들에서 뺄 수 있습니다.
- **검토한 대안**: React Router framework 모드. 파일 기반 라우팅과 SSR 기능이 있지만 빌드 구성이 바뀌고 지금은 필요 없습니다.

## D9. API 응답과 폼 입력은 Zod로 검증한다

- **날짜**: 2026-10-19
- **결정**: API 응답은 Zod 스키마로 `parse`한 뒤 쓰고, 타입은 `z.infer`로 스키마에서 뽑습니다. 폼은 React Hook Form + `zodResolver`로 만들고 검증 규칙은 스키마에만 씁니다.
- **이유**: TypeScript 타입은 실행 중에 확인되지 않습니다. 바이브 코딩으로 만든 코드가 실제 응답 형태와 어긋나면 그 자리에서 에러로 드러나야 합니다.
- **다시 볼 조건**: 백엔드 OpenAPI에서 Zod 스키마를 자동 생성하게 되면 손으로 쓰는 스키마를 생성 코드로 바꿉니다.

## D10. 백엔드의 snake_case 응답을 변환하지 않는다

- **날짜**: 2026-10-19
- **결정**: 백엔드 JSON 키가 snake_case(`started_at`)이므로 Zod 스키마와 타입의 키도 snake_case 그대로 씁니다. camelCase로 변환하지 않습니다.
- **이유**: 변환 코드가 없어 단순합니다. OpenAPI에서 생성한 타입을 그대로 쓸 수 있습니다.
- **검토한 대안**: axios interceptor에서 변환하는 방법은 생성된 타입과 키가 어긋나고 깊은 객체에서 예외가 생깁니다. Zod `transform`은 스키마마다 변환 코드가 늘어납니다.
- **다시 볼 조건**: 백엔드와 최종 확인 전입니다. 백엔드가 camelCase로 바꾸기로 하면 이 결정을 대체합니다.

## D11. 테스트는 Vitest + React Testing Library, E2E는 Playwright

- **날짜**: 2026-10-19
- **결정**: 로직과 입력 컴포넌트는 Vitest + RTL로, 실제 화면은 Playwright(Chromium)로 테스트합니다. 지금은 화면이 뜨는지 보는 스모크 테스트 1개만 있습니다.
- **이유**: 바이브 코딩에서는 AI가 쓴 코드가 맞는지 자동으로 확인하는 장치가 필요합니다. 단위 테스트는 라우팅이나 실제 렌더링 문제를 잡지 못해서 E2E도 함께 둡니다.
- **참고**: 3D 화면은 픽셀 비교를 하지 않습니다. 캔버스가 보이는지와 콘솔 에러가 없는지까지만 확인합니다. 테스트가 실패하면 테스트를 지우거나 기대값을 바꿔서 통과시키지 않고 코드를 고칩니다.

## D12. 3D는 three.js + React Three Fiber

- **날짜**: 2026-10-19
- **결정**: WebGL 3D는 three.js를 React Three Fiber로 씁니다. `<Canvas>`가 들어간 컴포넌트는 반드시 lazy로 불러옵니다.
- **이유**: React 컴포넌트처럼 씬을 작성할 수 있습니다. three.js 청크가 약 912 KB라 첫 화면 번들에 넣으면 안 됩니다.
- **다시 볼 조건**: 압축 모델 로딩이나 카메라 컨트롤이 필요해지면 `@react-three/drei`를 추가합니다. React를 19.4 이상으로 올리기 전에 R3F 지원 여부를 확인합니다.

## D13. 프론트는 Docker 없이 정적 파일로 배포한다

- **날짜**: 2026-10-19
- **결정**: 프론트 Dockerfile과 nginx 설정을 두지 않습니다. CI는 `npm ci && npm run check`로 검사와 빌드를 하고 결과물 `dist/`를 배포합니다.
- **이유**: 빌드 결과가 정적 파일이라 컨테이너가 없어도 됩니다. 서빙하는 서버 한 곳에서 SPA fallback과 `/api` 프록시를 함께 처리할 수 있습니다.
- **검토한 대안**: node 빌드 + nginx 서빙 이미지. 처음에는 이 방식으로 세팅했다가 뺐습니다.
- **다시 볼 조건**: 팀이 모든 서비스를 컨테이너로 배포하기로 하면 다시 추가합니다(10줄 정도).
- **보충 (2026-10-30)**: dev 자동 배포(S15P31A108-123, PR #52)는 빌드한 `dist/`를 `FROM scratch` 포장 이미지에 담아 서버로 옮깁니다. 이 이미지는 `infra/frontend-dist/`에 두고 실행하거나 서빙하지 않으며, 서빙은 호스트 Nginx가 그대로 하므로 이 결정과 충돌하지 않습니다. 배포 직후 열려 있던 탭이 예전 해시의 청크를 받지 못하면 `src/lib/reloadOnStaleChunk.ts`가 한 번 새로고침합니다.

## D14. Git hook 도구는 프론트에서 따로 넣지 않는다

- **날짜**: 2026-10-19
- **결정**: Husky, lint-staged, commitlint를 넣지 않습니다.
- **이유**: Git hook 경로는 레포 전체에 하나뿐이라 프론트만 따로 넣으면 다른 앱의 hook과 충돌합니다. 팀이 Jira 키 자동 삽입용 `prepare-commit-msg` hook을 도입할 예정입니다.
- **다시 볼 조건**: 팀 공용 hook이 도입될 때 프론트 검사(`npm run check`)를 거기에 붙일지 같이 정합니다.

## D15. 도입하지 않거나 미룬 도구

- **날짜**: 2026-10-19
- **Storybook**: 도입하지 않습니다. 짧은 프로젝트에서는 세팅과 유지 비용에 비해 얻는 것이 적습니다.
- **MSW**: API를 부르는 컴포넌트 테스트가 많아지면 검토합니다. 지금은 단위 테스트는 `vi.mock`, E2E는 `page.route`로 대체합니다.
- **md 부분 편집 기능**: 요구사항이 정해지면 블록 단위 편집(`react-markdown` + `mdast-util-from-markdown`)을 검토합니다.
- **AI 서버 직접 호출**: 하지 않습니다. 인증과 키 관리를 위해 백엔드를 거칩니다.

## D16. 기존 3D geometry를 보존하고 Canvas의 renderer를 주입한다

- **날짜**: 2026-10-23
- **결정**: 도시, 사무실, 실외 엔진의 기존 geometry·레이아웃·이동·카메라 계산을 유지합니다. 각 엔진은 선택적인 외부 `WebGLRenderer`를 받고, R3F Canvas의 `gl`을 공유합니다. `useFrame` 우선순위 1로 자동 렌더링을 인계받아 기존 렌더링 순서를 실행합니다.
- **이유**: 형상을 새로 작성하면 기존 부지, 가구, 캐릭터, 출입구, 가림 처리와 클릭 판정이 달라질 수 있습니다. renderer를 공유하면 Canvas마다 WebGL 컨텍스트가 하나로 유지됩니다.
- **소유권**: 외부 renderer의 canvas 삽입·제거, 크기·픽셀 비율 설정, renderer dispose·context loss는 Canvas가 맡습니다. 엔진은 자신이 만든 scene 자원을 정리합니다.
- **검사**: 기존 배치·이동 회귀와 외부 renderer 소유권 검사를 Vitest로 유지하며, WebGL 진입은 Chromium에서 확인합니다.

## D17. 브라우저 예시를 기본으로 하고 REST 계약 경계를 준비한다

- **날짜**: 2026-10-23
- **결정**: `VITE_API_MODE=mock`을 기본으로 사용하고 `live`일 때만 `/api`를 호출합니다. 명세의 108개 REST 경로와 요청·응답 스키마를 서비스 계층에 등록합니다. 예시 환경은 axios 어댑터로 처리하며 실제 네트워크로 대체 호출하지 않습니다.
- **이유**: 백엔드를 수정하거나 가동하지 않고도 프론트 흐름을 검토할 수 있고, 실제 연동 때도 같은 서비스 경계를 사용할 수 있습니다. 예시 값과 실제 AI·에이전트 활동을 구분해야 합니다.
- **참고**: 실제 백엔드 통합은 아직 검증하지 않았습니다. 인증·CSRF 및 세부 계약 확정 후 live 모드로 별도 검증해야 합니다. D15의 MSW 미도입 결정은 유지합니다.

## D18. API에 없는 공간 설정은 브라우저에 보관한다

- **날짜**: 2026-10-23
- **결정**: 사용자가 고르는 부지·외관과 시점 설정은 Zustand persist로 브라우저에 보관합니다. 부지·외관은 계정과 프로젝트 ID를 함께 키로 사용합니다. 프로젝트 이름·설명·멤버십 등 서버 데이터는 Query에서 읽습니다.
- **이유**: 현재 프로젝트 REST에는 부지·건물 저장 필드가 없습니다. 3D 선택 기능을 유지하기 위해 서버 계약을 임의로 늘리지 않습니다.
- **제한**: 브라우저 저장값은 다른 기기와 동기화하지 않습니다.
- **다시 볼 조건**: 팀이 공간 저장 API와 계정별 배치 정책을 확정할 때

## D19. 미정 content와 Git 확장 계약을 만들어 내지 않는다

- **날짜**: 2026-10-23
- **결정**: 세부 스키마가 미정인 구조화된 `content`는 JSON 객체 경계까지 검증합니다. Git·PR 등 요구사항에 있으나 REST 계약이 없는 확장은 상태 안내를 제공하고 실제 연결·게시 API를 임의로 호출하지 않습니다.
- **이유**: 프론트 내부에서 만든 형식을 확정된 팀 계약처럼 사용하면 실제 연동 시 의미와 필드가 어긋납니다. 문서 원문·버전·근거를 확인하는 흐름과 미정 구조를 분리해 유지합니다.
- **다시 볼 조건**: OpenAPI, content 스키마, Git 저장소·PR 인증 및 조회·게시 계약이 확정될 때

## D20. 공간 이동과 설계 승인 상태를 분리한다

- **날짜**: 2026-10-24
- **결정**: 프로젝트 준비 단계에서도 사무실의 보이는 바닥을 걸을 수 있다. 기준 설계 발행 여부는 업무 승인 절차에만 사용한다. 시점 전환과 업무 창 닫기 뒤에는 사무실 입력 포커스를 복원하고, 업무 창이 열려 있으면 이동 입력을 비운다.

## D23. 비밀번호는 서버 정책(Q04)과 같은 규칙으로 검사한다

- **날짜**: 2026-11-02, Q04 결정 반영 2026-11-06
- **결정**: 회원가입·비밀번호 변경·비밀번호 찾기의 비밀번호 칸은 서버 `PasswordPolicy`와 같은 규칙으로 검사한다(`src/features/auth/passwordRule.ts`). Q04에서 정한 규칙(2026-11-06, PR #180)은 8자 이상, UTF-8 72바이트 이하, 영문·숫자 각 1자 이상이다. 오류는 상황별로 나눈다(사용자 결정): 8자보다 짧으면 '8자 이상으로 입력하세요.', 72바이트를 넘으면 '비밀번호가 너무 길어요. 더 짧게 입력해 주세요.', 종류가 빠지면 '영문과 숫자를 모두 넣어 8자 이상으로 입력하세요.' 뒤에 빠진 종류를 붙인다. 안내 문구에 바이트·글자 수 상한은 쓰지 않는다. mock도 같은 규칙으로 거절한다.

- **제한**: 로그인 칸은 이 규칙을 걸지 않는다.
- **다시 볼 조건**: 서버 비밀번호 정책(Q04)이 바뀔 때

## D25. E2E는 새 headless Chromium으로 워커 1개에서 돌린다

- **날짜**: 2026-11-03
- **결정**: `playwright.config.ts`의 chromium 프로젝트에 `channel: 'chromium'`을 두고 `workers: 1`로 테스트를 한 번에 하나씩 돌린다.
- **이유**: 기본 headless shell은 WebGL을 SwiftShader(CPU 소프트웨어 렌더링)로 그린다. 이 렌더링에서 사무실 한 프레임은 3인칭 0.5~1초, 1인칭 1.4~2초 걸리고, Playwright 조작은 프레임이 끝날 때까지 기다린다. 1인칭 프레임이 약 1.2초를 넘으면 위치를 한 번 읽는 데 5초 poll 제한을 넘겨 `movement.spec.ts:34`가 실패했다. 워커 1개로도 6번 중 6번 실패했고, 기본 워커(22코어 PC에서 5개)에서는 실패가 더 늘었다. 새 headless(`channel: 'chromium'`)는 GPU를 써서 프레임이 약 10ms다. 같은 커밋에서 전체 10개가 22~26초에 3번 연속 통과했다(이전 SwiftShader 워커 1개는 3.9분). 워커를 여러 개 두면 콜드 스타트 중 사무실 로딩이 5초 제한을 넘는 일이 있어 1개로 둔다.
- **제한**: GPU가 없는 PC에서는 새 headless도 SwiftShader로 돌아가 위의 시간 초과가 다시 날 수 있다. 다른 worktree나 세션의 E2E와 동시에 돌려도 느려질 수 있다. 브라우저는 `npx playwright install chromium`이 설치하는 일반 Chromium을 쓴다(`--only-shell`로 설치하면 없다).
- **다시 볼 조건**: CI에서 E2E를 돌리게 될 때, 또는 E2E가 3D 화면 없이 도는 흐름으로 나뉠 때

## D32. 가입 이메일 인증은 mock 어댑터가 서버 판정 순서를 따르고, 예시 코드는 mock 모드에서만 보인다

- **날짜**: 2026-11-04
- **결정**: 가입 이메일 인증(ACC-A11·A12)은 live와 mock이 같은 `authApi` 호출을 쓴다. mock 규칙은 `src/mocks/emailVerifications.ts`에 두고 PR #114 `EmailVerificationService`의 판정 순서와 오류 코드를 따른다: 코드 5분, 이메일당 1시간 5회, 틀린 입력 5회(다섯 번째가 429 `too_many_attempts`, 그 뒤 맞는 코드도 429), 확인한 코드 재사용은 410, 토큰 1회용. 다시 받기 60초와 토큰 30분은 서버(PR #114 `application.yml`) 기본값과 명세 응답 예시를 따른다(사용자 결정). 서버 응답에는 코드가 없으므로 계약 스키마에 넣지 않고, mock 모드에서만 화면이 mock 모듈을 동적 import해 방금 보낸 코드를 '예시 코드'로 보여 준다.
- **이유**: 코드 유효 5분은 명세 처리 규칙이고, 다시 받기 60초는 ACC-A11 응답 예시(`expires_at`·`resend_available_at`의 1분 차이), 토큰 30분은 ACC-A12 응답 예시에서 온 서버 기본값이다. mock이 서버와 같은 값이어야 mock으로 본 흐름이 live와 같다. live 화면은 서버가 준 `resend_available_at`·`expires_at`으로 센다. 예시 코드를 스키마 밖에 두면 live 빌드에 mock 청크가 생기지 않는다(D17).
- **제한**: mock 인증 상태는 메모리에만 있어 새로고침하면 사라진다. 틀린 횟수가 오류 응답 뒤에도 남아야 해서 실패하면 되돌리는 예시 DB(`state.ts`)에 두지 않았다.
- **다시 볼 조건**: Q04에서 다시 받기 간격·발송 한도·토큰 유효 시간이 정해질 때

## D26. 발행 후 분석은 기존 변경 제안 상세에서 확인한다

- **날짜**: 2026-11-04
- **결정**: CHG-A03의 `published_analysis`를 변경 제안 상세에 표시한다. 승인 전 영향 분석(CHG-A05)과 발행 후 처리는 별도이며, 실패·미평가·근거 부족·미확인을 완료나 영향 0건으로 바꾸지 않는다. 대기·실행 중에는 상세를 15초마다 새로 확인하고 모든 상태에서 수동으로 새로고침할 수 있다.
- **대기 안내**: PENDING의 접수 시각부터 브라우저가 확인한 시각까지 10분 이상이면 '오래 대기 중'으로 안내한다. 브라우저 시계 오차와 자동 재시도가 포함되며 consumer가 의도적으로 꺼져 있을 수도 있어 장애라고 단정하지 않는다. 이는 #244의 `600초 초과 + 5분 지속 + consumer 활성화` 운영 알림과 별개다.
- **연계**: 대시보드 활동의 기존 변경 제안 링크를 사용한다. 새 프로젝트별 CDC 집계 API나 checkpoint를 만들지 않는다. MCP #221과 Grafana #244의 실제 연동·권한 및 알림 검증은 각 담당 작업에서 확인한다.
- **제한**: 브라우저 mock은 발행 후 분석 워커가 없으므로 발행된 제안의 상태를 `UNKNOWN`으로 응답한다. 실제 서버 연동은 별도의 배포 환경에서 확인해야 한다. 수동 재처리 API는 현재 없어 화면에 재처리 버튼을 두지 않는다.

## D33. 나의 도시는 원형 고리를 앞쪽 호만 보이게 그린다

- **날짜**: 2026-11-03
- **결정**: 도시 화면은 캔버스 SCR-04-v2-city(v474)의 원형 도시다. 칸 12개가 반지름 286(칸 간격 150, 칸 각도 30°)의 고리에 놓이고(`src/three/city/ring.ts`) 고리가 통째로 돈다. 화면은 고리 앞쪽 호만 담아 보이는 부지가 가로로 한 줄 선 큐처럼 보인다(사용자 "아니 원형을 유지하면서 그렇게 보이도록하라고한거야", 캔버스 미리보기 city-ring-queue-preview 4번, 사용자 결정 '12칸 유지'). 카메라는 정사영·고도 45°·방위 45°이고, 1310px 화면에 860단위를 담고(좁은 화면은 400단위까지) 앞 칸의 땅을 화면 높이 75%에 둔다. 좁은 세로 화면에서 고리 전체가 원으로 보이지 않게 도시 칸의 높이는 폭의 80%를 넘지 않는다. 양 끝 칸은 가라앉지 않고 고리를 따라 뒤로 돌아 화면 밖으로 나간다(v474의 줄어들기는 뺐다). 부지 모양은 프로젝트 칸과 빈 부지 하나에만 두고, 빈 부지는 늘 마지막 프로젝트 다음 칸이다. 프로젝트를 지우거나 나가 칸이 비면 남은 프로젝트를 원래 순서대로 앞 칸부터 당겨 중간에 빈 칸을 남기지 않는다(사용자 요청 "프로젝트를 삭제하거나 나가면 중간이 비어지게 되는데 당겨지도록 수정해", S15P31A108-256). 저장된 칸 번호는 순서로만 쓰고 외관은 칸이 아니라 프로젝트를 따라가며, 프로젝트를 만들거나 외관을 저장할 때 지금 보이는 칸 번호를 함께 저장해 번호가 겹치지 않게 한다. 쓰지 않은 칸은 잔디·나무·벤치·꽃밭으로 채운다. 주변(순환 도로·보도·가로수·공원·가로등·벤치·흐린 먼 건물)은 고리와 같이 돈다. 건물 정면은 고리 바깥(카메라 쪽)을 본다. 끌거나 휠(트랙패드 스크롤)을 굴려 돌리고, 멈춤 자리는 프로젝트 칸과 빈 부지뿐이다. 휠은 250px마다 다음 멈춤 자리로 가서, 빈 부지에서 한 번 굴리면 꾸밈 칸을 한 번에 지나 1번이 가운데로 오고 1번에서 거꾸로 굴리면 빈 부지로 온다(사용자 결정 '꾸밈 구간 한 번에 넘기기'). 끌고 놓으면 가장 가까운 멈춤 자리로 간다. 끌기·휠은 캔버스와 그 위 이름표를 함께 담은 도시 영역에서 받아 이름표 위에서도 고리가 돌고, 도시 위에서만 페이지 스크롤을 막는다. 확대·축소는 없다(사용자 요청). 도시에 들어오면 이 계정이 이 브라우저에서 마지막으로 연(워크스페이스를 연) 프로젝트 건물이 가운데에 온다(사용자 요청 "가장 마지막에 방문한 프로젝트 건물이 가운데로"). 서버에 최근 방문 값이 없어 부지 배치처럼 계정별 브라우저 설정(`workspaceStore.lastVisited`)에 남긴다. 기록이 없거나 그 프로젝트를 지웠거나 나가 도시에 없으면 가장 최근 칸이 가운데, 빈 부지가 그 오른쪽이다. 이름표는 HTML 버튼이라 키보드로도 들어가거나 만들 수 있고, 도시 위에 겹친 제목·설명·만들기 버튼과 겹치거나 화면 끝에서 잘리거나 이웃 이름표와 겹치면 숨긴다. 프로젝트 만들기 창을 열면 도시가 화면 전체에 깔리고, 창의 흐린 막 뒤로 보인다(SCR-04-v2-create-project). 로그인 화면의 도시 그림(`src/assets/city-preview.webp`)은 이 화면을 찍은 정적 그림이다.
- **이유**: 사용자가 캔버스에서 확정한 원형 도시 구조를 유지하면서, 칸 순서를 가로 한 줄로 읽히게 하려는 것이다. 한때 곧은 거리 하나를 따라 늘어선 일직선 순환 큐(3ff091d)로 바꿨으나 사용자가 뜻한 것이 아니어서 고리로 되돌렸다. 꾸밈 칸에 멈추지 않게 해 빈 부지와 1번 사이의 꾸밈 칸(프로젝트 6개면 5칸)을 한 번에 넘긴다. 격자 8칸 도시의 공사 미리보기·통근 로봇·자동차는 원형으로 옮길 때 지웠고, 도시 화면은 D16의 기존 geometry 보존 대상에서 빠진다.
- **제한**: 칸 수는 12로 고정이다. 12칸 고리는 보이는 칸이 고리의 큰 몫이라 양 끝 칸이 화면 위쪽으로 휘어 오르고 고리 중심(벌집)이 화면 위쪽에 보인다(미리보기 README는 24칸을 추천했다). 저장된 자리가 없는 프로젝트도 앞 칸부터 12칸까지 자동으로 놓고(`src/features/projects/placements.ts`), 넘는 프로젝트는 부지 없이 목록에만 남는다. 먼 건물은 캔버스의 building-c·k가 레포에 없어 building-a·g로 대신한다.
- **다시 볼 조건**: 프로젝트가 12개를 넘는 사용자가 생기거나, 부지·건물 저장이 서버 계약이 될 때

## D41. 나의 도시의 호버 카드는 올린 프로젝트만 불러오고, 배지는 알림 한 번으로 센다

- **날짜**: 2026-11-06
- **결정**: 프로젝트 카드는 건물 그림·이름·설명만 두고, 역할·상태·숫자·인원·최근 활동은 호버 카드로 옮긴다. 호버 카드는 올린 프로젝트 하나만 기존 API(MON-D01·C01·T01, PRJ-A06, MEM-A06, MON-A04)로 불러오며 사무실 HUD와 같은 키를 쓴다. 배지는 NTF-A01을 `project_id` 없이 `unread=true&limit=100`으로 한 번 불러 항목의 `project_id`로 센다. 호버 카드는 Radix HoverCard 대신 상태로 그린다. 지도에서는 트리거가 3D 건물이라 DOM 요소가 없고, 자리가 트리거 옆이 아니라 고정 자리이거나 카드 위에 겹치는 자리라 Popper 배치를 쓸 곳이 없기 때문이다. 터치에는 호버가 없어 배지만 보인다.
- **이유**: 목록 API에 요약을 넣는 수정안(PR #179)은 백엔드 작업과 목록 응답 비용이 든다. 호버 때만 부르면 목록은 그대로이고 프로젝트 N개를 처음에 한꺼번에 부르지 않는다.
- **제한**: 안 읽은 알림이 100건을 넘으면 프로젝트별 수가 모자랄 수 있어 벨 팝오버처럼 `3+`로 보이고, 최신 100건에 하나도 없는 프로젝트는 배지가 빠진다.
- **다시 볼 조건**: NTF-A01에 프로젝트별 안 읽은 수가 생기거나, 카드에 숫자를 호버 없이 보여야 할 때

## D34. 사무실 캐릭터는 회원 설정 캐릭터(avatar)로 그린다

- **날짜**: 2026-11-02
- **결정**: 사무실의 '나'는 세션 계정의 avatar로 모양을 정한다(`src/three/office/office-actors.ts`의 `avatarAppearance`). 옛 `bee-*` 값은 회원 설정과 같은 규칙(`characterOf`)으로 가장 가까운 새 캐릭터, 값이 없으면 사람이다. 3D 모양은 회원 설정 그림(캔버스 SCR-05-v2-account v440)과 같은 모델이다.

  | avatar  | 사무실 모양    | 3D 모델                                                                                            |
  | ------- | -------------- | -------------------------------------------------------------------------------------------------- |
  | `human` | `human`        | Kenney Mini Characters `character-female-d`(CC0, `public/models/kenney/characters/`), 팔 ±1.15 rad |
  | `robot` | `member-robot` | 캔버스가 보드 그림을 만든 로봇(`src/three/office/memberFigures.ts`)                                |
  | `bee`   | `bee`          | 캔버스가 보드 그림을 만든 벌(같은 파일)                                                            |

  셋을 보드처럼 같은 키(1.5타일)로 맞추고, 기존 걸음·앉기 자세가 팔·다리·머리를 돌린다. 로봇·벌은 보드 모델의 팔·다리를 어깨·엉덩이 축 그룹으로만 묶었다(서 있는 모양은 같다). 블록 캐릭터는 다리가 짧아 앉을 때 직접 만든 로봇의 엉덩이 높이(0.59)까지 올린다. 다른 팀원은 팀원 목록(MEM-A06)에 avatar가 없어 사람으로 그리고(D35), 목록에 `avatar`가 오면(선택 필드로 받아 둠) 그 모양으로 그린다.

- **이유**: 회원 설정에서 캐릭터를 바꿔도 사무실의 나는 늘 같은 사람 모양이었다(사용자 지적 2026-11-02). 회원 설정 그림이 Kenney 사람 모델과 캔버스 로봇·벌 모델로 만들어졌으므로, 같은 모델을 쓰면 2D 그림과 3D 사무실이 같은 캐릭터로 보인다. D21에서 되돌린 Kenney 사람 모델을 다시 쓰는 이유가 이것이다.
- **제한**: 사람 모델은 받는 동안 바닥 그림자만 보이고, 받지 못하면(단위 테스트) 몸이 없다. Kenney 모델의 걸음·앉기 애니메이션은 쓰지 않고 기존 자세 코드로 움직인다(팔꿈치·무릎 뼈가 없어 팔다리가 곧게 움직인다). 직접 만든 사람 모양(정장 차림)은 쓰지 않게 되어 지웠다. 1인칭 눈높이는 모양과 상관없이 그대로다.
- **다시 볼 조건**: 팀원 목록에 avatar가 오거나, 회원 캐릭터가 늘거나 보드 그림이 바뀔 때

## D35. 사무실의 AI 에이전트·비비는 캔버스 캐릭터로 그리고, 비비는 GLB 파일 하나에서 읽는다

- **날짜**: 2026-11-03
- **결정**: 캔버스 SCR-06-rec-office-chars의 캐릭터를 사무실에 옮긴다. 가구와 공간은 D36에서 옮겼다.

  | 누구               | 모양                                                                                        | 키               |
  | ------------------ | ------------------------------------------------------------------------------------------- | ---------------- |
  | 팀원               | 계정 avatar(사람·로봇·벌, D34). 모르면 사람                                                 | 1.7 m(1.5타일)   |
  | 팀원의 AI 에이전트 | 하늘색 포인트 흰 로봇(`src/three/office/agentFigure.ts`, v485). 목 스카프·왼팔 띠가 주인 색 | 안테나 끝 1.74 m |
  | 비비(AI 팀장)      | `public/models/bibi.glb`(BEEBEE Studio, 3.9 MB, 뼈 7개, Idle·Walk·Wave)                     | 1.35 m           |

  비비는 고정 사무실에서 단계와 관계없이 보인다. 이전에는 프로젝트를 시작하면 lead 에이전트가 사무실 목록에서 빠져 비비가 보이지 않았다. 서는 자리는 비비 현재 상태(BEE-A04, HUD 비비 줄과 같은 `beeStatusQuery`)를 따른다(2026-11-09 고침, S15P31A108-306). 처음의 사용자 결정 '라운지 가운데에 세움'은 한가할 때의 자리로 남는다.

  | 상태(`activity`)                 | 자리                                                 |
  | -------------------------------- | ---------------------------------------------------- |
  | `DOCUMENT_REVIEW`                | '공용 문서함' 구역 입구, 열람 테이블 남쪽            |
  | `MEETING`                        | '회의실' 구역. 배치마다 테이블 옆(`plans/<외관>.ts`) |
  | `IDLE`, 상태 없음, 없는 API(404) | 라운지 가운데 lead 자리                              |

  상태 → 자리 계산은 `office-actors.ts`의 `bibiSpot`이고, 두 구역의 자리는 배치마다 `bibiSpots`에 있다(자리는 구역 안 빈 칸이고, 의자에서 사람 사이 거리만큼 떨어져 있으며, 회의실·문서함·워룸 자리가 다 차도 드나들 수 있다. 방을 26 × 14 m로 좁힌 뒤(D42) 열람 테이블 동쪽은 앉은 사람 옆을 지나야 하는 한 칸 통로라 구역 입구에 선다. 유리 회의실은 테이블 머리가 TV장과 앉은 사람 사이에 끼고 동쪽 끝이 북쪽 자리로 가는 길이라 TV 옆 서쪽에 선다). 상태가 바뀔 때만 새 자리로 걸어가 머물고(D37 에이전트와 같은 길찾기·사람 사이 거리 규칙), 산책하지 않는다. 걸을 때는 GLB의 Walk를 돌린다. 서 있는 비비에게 내가 2칸 안으로 다가오면 Wave를 한 번 돌리며 나를 보고, 3칸 밖으로 멀어져야 다시 흔든다(`motion.ts`의 `bibiWave`, 경계에서 되풀이하지 않게 들어옴과 나감을 나눴다). 화면을 열 때 처음 읽은 자리에는 걷지 않고 바로 선다. 상태를 아직 읽지 못했거나 첫 조회가 실패하면 라운지에 있고, 다시 부르다 실패하면 마지막으로 받은 자리에 있는다.

  에이전트는 HUD 팀 목록처럼 연결된 팀원의 에이전트와 아직 연결하지 않은 내 에이전트를 그린다. 상태 넷 중 연결 전은 회색 몸·꺼진 화면·고개 떨굼·빨간 X로 자리에 있고, 연결됨은 하늘색, 주인에게 진행 중 작업이 있으면 작업 중(노랑)이다. 대기(회색 불빛·감은 눈·등 기대기)는 모델에 있지만 에이전트 활동 API가 없어 아직 쓰지 않는다. 직접 만든 기본 로봇(검은 바이저)은 지웠고, avatar를 모르는 팀원은 사람으로 그린다(사용자 결정).

- **이유**: 사용자가 캔버스에서 고른 캐릭터다. 비비는 사용자가 이미지→3D 도구 등으로 더 나은 모델을 만들 수 있어, 코드를 고치지 않고 파일만 바꾸면 교체되게 했다(앞 = +z, 발바닥 y = 0인 GLB면 1.35 m로 맞춰 세운다). 2026-11-03에 캔버스 v482 귀여운 비비(0.83 MB, 관절 없음)를 사용자가 보낸 BEEBEE Studio 에셋의 `beebee_studio.glb`로 바꿨다. 사용자가 준 BEEBEE 디자인 시트로 재구성한 모델이다(삼각형 111,622개, 재질 9개, glTF 검증 오류·경고 0). 에셋에 함께 든 three.js 뷰어(MIT)·Blender 원본·렌더 그림은 레포에 넣지 않았다.
- **제한**: 에이전트가 늘면 사무실 책상 수도 늘어난다(인원으로 배치를 만드는 기존 방식). 에이전트의 앉기·걷기는 기존 자세 코드가 어깨·팔꿈치·엉덩이·무릎을 돌려 만든다(캔버스의 사무 동작 자세 전부는 아니다). 비비 GLB에는 뼈 7개(Root·Body·Head·Arm_L·Arm_R·Leg_L·Leg_R)와 Idle·Walk·Wave 애니메이션이 있다. 서 있으면 Idle, 걸으면 Walk(제자리 걷기)를 AnimationMixer로 돌리고, Wave는 쓸 곳이 없어 아직 쓰지 않는다. 삼각형이 이전보다 많아, 비비가 보이는 사무실 시점에서 프레임 제한을 풀고 잰 프레임 시간이 평균 약 1 ms 늘었다(이전 모델 9.1 ms → 10.0 ms, 4번씩 번갈아 잰 평균. 60 fps 예산 16.7 ms 안).

## D44. Vitest 시험 한도는 15초, findBy·waitFor 대기는 3초로 늘린다

- **날짜**: 2026-11-09
- **결정**: `vite.config.ts`의 `test.testTimeout`을 15초로, `src/test/setup.ts`에서 Testing Library `asyncUtilTimeout`을 3초로 둔다. 워커 수(`maxWorkers`)는 기본값 그대로 둔다. 번호 D43은 열린 PR #230이 쓰고 있어 건너뛴다.
- **이유**: 22코어 PC에서 `npx vitest run`을 돌리면 매번 다른 시험 0~14개가 5초 한도나 findBy 1초를 넘겨 실패했다. 모두 입력 흉내(`userEvent.type`)가 많은 화면(가입·비밀번호·탈퇴·변경 제안 등)이고, 그 파일만 따로 돌리면 1.0~2.1초에 통과한다. 워커가 많이 뜨고 다른 세션의 빌드가 CPU를 같이 쓰면 서너 배 느려진다. 한도를 늘려도 통과하는 시험은 기다리던 것이 오는 즉시 끝나므로 전체 시간은 늘지 않는다.
- **버린 안**: 워커 수를 50%·25%로 줄이면 실패는 사라졌지만(2회씩 실패 0) 25%는 63~65초로 느려졌다. CI(4코어)에도 같이 걸려 CI가 느려지고, 로컬만 줄이려면 환경별 분기가 필요하다.
- **제한**: 정말 멈춘 시험은 실패할 때까지 15초(findBy는 3초)를 기다린다. 한도를 넘는다면 부하보다 시험이나 화면을 먼저 의심한다.
- **다시 볼 조건**: 한도를 넘는 실패가 다시 나거나, CI에서 시험 시간이 크게 늘 때

## D45. 비비 검토가 무효인지는 서버가 작업본 응답으로 알려 주고, 화면은 해시를 계산하지 않는다

- **날짜**: 2026-11-10
- **결정**: 작업본 조회(`working-copy`)의 `review_stale`(S15P31A108-362)을 믿고 `reviewStage()`가 "다시 검토 필요" 단계(`stale`)를 만든다. 이 단계에서는 예전 제안·팀장 검토 요청·직접 요청 폼을 숨기고, 자동으로 다시 검토하지 않고 "비비 검토 다시 받기"만 보인다. 409 `review_stale`을 맞은 검토 id를 모듈 변수에 기억하는 방식은, 서버 판정에 없는 경우(앞 제안을 반영해 다음 제안의 원문이 사라짐)의 보조로만 남긴다.
- **이유**: 참고 승인본이 바뀌어도 revision은 그대로라 화면은 409를 한 번 맞기 전에는 무효를 알 수 없었다. 그래서 필수 문서 4종을 차례로 승인하는 동안 목록과 상세가 예전 검토를 그대로 보였다.
- **버린 안**: 화면에서 `reference_hash`를 비교하는 안. 서버만 승인본 집합을 알고, 해시 규칙을 화면에 복제하면 서버와 어긋난다. 자동 재검토도 뺐다. 회당 12~17초와 토큰 비용이 들고 사용자가 보지 않은 문서까지 돌린다.
- **제한**: `review_stale`은 작업본 응답에만 있다. 서버가 아직 값을 주지 않으면(없음) 지금처럼 false로 보고 409로 알게 된다. `review_stale` 409의 문구는 본문·참고 승인본·원문 소실을 가리지 않는 말로 쓴다.
- **다시 볼 조건**: 서버가 무효 원인(`stale_reason`)을 내려 주어 문구를 원인별로 나눌 때, 서버 값이 배포돼 409 기반 보조 기억이 필요 없어질 때

## D46. 업무 창이 열려 있어도 입력칸에 쓰는 중이 아니면 숫자 키로 메뉴를 바꾼다

- **날짜**: 2026-11-10
- **결정**: 업무 창이 열려 있을 때 숫자 키 1~6을 누르면 단축 바 칸을 누른 것처럼 그 창으로 바꾼다. 열린 창의 번호를 다시 누르면 지금처럼 닫는다. 포커스가 입력칸(`input`, `textarea`, `select`, `contenteditable`)에 있으면 숫자는 글자로 들어가고 창을 바꾸지 않는다. 창 안의 버튼·링크·본문에 포커스가 있으면 바꾼다. 잠긴 칸으로는 바꾸지 않고, 설정 창이 열려 있으면 단축 바가 창 아래에 덮이므로 숫자 키도 무시한다. 감사 배치 A(커밋 9f4f0114, 10-30)의 "창이 열려 있으면 그 창의 번호로 닫기만 하고 다른 번호는 무시한다"를 바꾼다(`Hotbar.tsx`).
- **이유**: 11-10 QA(S15P31A108-371 4번)에서 화면 안내는 "숫자 키로 메뉴 열기"인데 창이 열려 있으면 다른 번호가 먹지 않았다. 사용자가 입력칸에 쓰는 중일 때만 예외로 두기로 정했다(11-10).
- **제한**: 하위 화면(PaneSheet)에 쓰던 내용이 있어도, 포커스가 입력칸 밖(버튼, 빈 곳)에 있을 때 숫자를 누르면 확인 없이 창이 바뀌어 쓰던 내용을 잃을 수 있다. 9f4f0114가 다른 번호를 막았던 이유다.
- **다시 볼 조건**: 숫자 키로 창이 바뀌어 쓰던 내용을 잃었다는 제보가 나올 때, 하위 화면이 닫기 전에 확인을 묻게 될 때
