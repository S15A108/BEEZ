## 참고 2. 접근 거부 세부 규칙 (BE용)

**검사 순서.** 처음 걸린 단계의 응답을 돌려준다.

1. 인증 실패(세션 만료, 토큰 폐기, 에이전트 토큰으로 `/api/**` 호출) → 401
2. 프로젝트가 없거나 삭제됨, 호출자가 활성 멤버가 아님 → 404
3. 대상 객체가 그 프로젝트 소속이 아님 → 404
4. 남의 비공개(PRIVATE) 기록 → 404
5. 팀장·작업 담당자·작성자 조건 미충족 → 403

**프로젝트를 어디서 정하나.** `/api/projects/{id}`는 경로, `/mcp`는 토큰에서 정한다. `/api/human/**`은 경로의 대상 객체의 프로젝트로 정하고, 본문 `project_id`가 다르면 404다. 대상이 없는 `POST /api/human/baselines`만 본문 값으로 정한다. 클라이언트가 보낸 `project_id`·`X-Project-Id`는 대조만 하고 근거로 쓰지 않는다.

**목록·검색.** 필터로 넣은 ID(예: `task_id`)가 다른 프로젝트 것이면 오류 없이 0건이다. 권한 조건은 페이지·검색·집계 전에 건다.

**상황별 결과** (-208 인수 시나리오 후보)

| 상황 | 결과 |
| --- | --- |
| A 멤버가 B 프로젝트의 작업 ID로 조회 | 404, 없는 작업과 같은 응답 |
| A 토큰으로 B의 contextId를 `read_context`에 전달 | `not_found`, 감사 기록 남김 |
| 같은 프로젝트 안의 남의 비공개 기록 조회 | 404, 검색 결과·개수에서도 빠짐 |
| AI 질의·분석·요약이 B 또는 남의 비공개 내용을 근거로 씀 | 불가. AI 입력에는 권한 검사를 통과한 데이터만 |
| MCP 인자 `project_id`가 토큰 프로젝트와 다름 | `not_found` |
| 제외 직후 그 사람의 세션 / 토큰 | 다음 요청부터 404 / 401 `token_revoked` |
| 팀장 위임 직후 이전 팀장이 승인 요청 | 403 |
| 삭제된 프로젝트 | 모든 사용자 404 |

**구현 메모**

- 인증은 Spring Security가 경로별로 나눈다(`/api/**` 세션, `/mcp` 토큰, 그 밖은 헬스체크·문서만).
- 서비스는 호출자를 `CallerContext`(계정·토큰·사람/에이전트) 인자로 받는다. REST는 컨트롤러 인자로 자동 주입되고, MCP 어댑터도 같은 값을 넘겨 같은 서비스를 부른다.
- 서비스 첫 줄에서 `ProjectAccessChecker.requireMember(caller, projectId[, LEADER])`를 호출한다. 반환값 `ProjectActor`에 `accountId`·`memberId`·`role`·행위자 종류·`agentTokenId`가 있어 담당자 판정과 작성자 기록에 쓴다. 사람 전용은 `actor.requireHuman()`, 담당자·작성자 조건은 `actor.requireMemberId(id)`. 자세한 사용법은 [06 문서](06-project-access.md).
- `project_id` 칸이 없는 테이블(`validation`, `task_plan_revision` 등)은 상위 객체와 조인한다. 예: `JOIN task t ON t.id = v.task_id WHERE v.id = ? AND t.project_id = ?`.
- 검증 워커는 접수 시점 권한으로 실행을 끝내고 결과를 저장한다. 그 결과를 쓰는 다음 요청(작업 시작 등)에서 권한을 다시 검사한다.
- 비비·RAG 응답은 다르다. BE가 최종 반환 직전에 현재 멤버십·검색 범위·baseline을 다시 확인하고, 생성 중 baseline이 바뀌었으면 그 답변을 버린다([RAG 개발 계획](../superpowers/plans/2026-10-26-document-rag-development.md) Task 5).
- 거부 응답은 `AccessErrors`로만 만든다. 404 메시지는 API 명세 오류표 문구 "리소스가 없거나 프로젝트 소속·접근 권한이 없음" 하나로 통일하고, 실제 사유(`cross_project`, `not_member` 등)는 서버 로그에 남긴다. 403은 code `forbidden`에 사유 메시지를 담는다(예: "팀장은 보고가 끊긴 작업만 취소할 수 있습니다"). FE는 메시지 문자열이 아니라 code로 분기한다. `mcp_audit_log`에 `deny_reason` 칸을 -178에서 추가한다.
- 벡터 검색은 조건을 붙이면 결과가 요청 개수보다 적게 나올 수 있다. 이때 프로젝트·접근 권한·허용 문서 버전·색인 준비(READY)·임베딩 프로필 조건은 **그대로 둔 채** 후보 수나 탐색량만 늘린다. 그래도 모자라면 적은 결과 또는 근거 부족을 돌려준다. 결과가 적다는 이유로 미승인 문서나 과거 baseline까지 넓히지 않는다. READY·임베딩 프로필은 [RAG 개발 계획](../superpowers/plans/2026-10-26-document-rag-development.md)의 용어다.

## 참고 3. 이미 정해진 것

새로 합의할 필요 없는 규칙과 근거다.

- 다른 프로젝트 객체는 404, `X-Project-Id`는 권한 근거 아님, 권한 필터는 페이지·집계 전 — [API Common](../api/00-common.md) 2·3절
- MCP 프로젝트는 토큰에서 결정, 매 호출 토큰·멤버십·소속 확인 — [MCP Tools](../api/02-mcp-tools.md) "연결과 인증"
- 권한 없는 PRIVATE는 not_found, 요약·개수에도 적용 — MCP-06, Backend REST CTX 절
- AI 입력에는 backend가 권한 검사한 데이터만 — [AI Internal](../api/03-ai-internal.md) 공통 규칙
- 제외·나가기 후 토큰 즉시 사용 불가, 탈퇴 시 토큰 전부 폐기, 프로젝트 삭제 시 접근 차단 — Backend REST MEM-A09·A10, ACC-A10, PRJ-A05
- 열린 작업이 남은 팀원의 제외·나가기는 409 `active_tasks_exist`, `reassign_to_member_id`로 인계 대상 지정 — Backend REST MEM-A09·A10
- 에이전트는 MCP 전용. REST API는 모두 세션 인증(Cookie)이고 Bearer 토큰을 받는 REST API는 없다 — Backend REST 각 API "인증", [시스템 아키텍처](01-system-architecture.md)

합의가 끝나면 1·3·4번 규칙을 API Common 2절에도 옮겨 기준을 한 곳으로 모은다. 남은 문서 정리: Backend REST CTX-A03에 "비작성자 PRIVATE는 404" 명시, MCP-06의 404 메시지 통일(변준성), [작업 생명주기](04-task-lifecycle.md) 6절 "제외된 팀원의 진행 중 작업" 행을 4번(409 `active_tasks_exist` 인계)과 Q05로 정리(변준성), Backend REST 오류표의 401 문구 "세션 또는 에이전트 인증" → "세션 인증"(전진).
