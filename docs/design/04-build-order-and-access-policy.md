### 용어·참조

- **명세**: 노션 요구사항 명세 DB. POL은 정책, AC는 인수 기준(완료를 판정할 시나리오 후보)이다. 명세에서 POL·AC는 모두 `검토`(팀 미확정) 상태다.
- **API 문서**: [API Common](../api/00-common.md), [Backend REST](../api/01-backend-rest.md), [MCP Tools](../api/02-mcp-tools.md), [AI Internal](../api/03-ai-internal.md). Q01~Q13은 API Common 9절의 검토 항목이다.
- **티켓**: `S15P31A108-` 접두어를 생략한다. 예: -170 = S15P31A108-170.
- **응답 코드**: 401 = 로그인·토큰이 필요하거나 무효, 403 = 대상은 보이지만 권한이 없음, 404 = 대상이 없는 것처럼 응답(존재 자체를 숨김).

- **G1·G3**: 작업 착수 전 검증(G1)과 작업 완료 검증(G3). 기획서의 게이트 번호다.

## 1. 요약

이 문서가 팀에 동의를 구하는 것:

1. **구현 순서**: 명세 POL-12의 순서(승인 설계·계약 → 규칙 검증 → AI·MCP → 화면 → 효용 실험) 앞에 **0단계(계정·프로젝트·멤버십·인증)** 를 둔다. 1단계의 API가 전부 멤버·팀장 검사를 전제로 하기 때문이다(4절).
2. **접근 거부 규칙**: 다른 프로젝트 객체나 남의 비공개 기록은 **404**(없는 것처럼), 같은 프로젝트 안에서 권한만 모자라면 **403**으로 거부한다. 검사 순서를 모든 REST·MCP API에서 똑같이 쓴다(5-2).
3. **권한 회수**: 팀원 제외·나가기·탈퇴·프로젝트 삭제는 **다음 요청부터** 반영한다. 멤버십·역할은 캐시하지 않고 매 요청 DB에서 조회한다(5-4).

일정에 주는 영향:

- 0단계(Sprint3, 10-26~10-31)가 늦으면 작업 계획(-156, 변준성)·문서(-192, 오서현)가 실제 권한 검사 없이 개발된다. 그래서 **-170 첫 PR에서 접근 검사의 호출 방법과 테스트용 구현을 먼저 dev에 올린다**(목표 10-28). Sprint3 목표의 "목 데이터로 병렬 개발"과 같은 방식이다.
- MCP 도구 연결(-176~-179)이 Sprint4(11-02~11-09)에 몰려 있어 에이전트 쪽 시연은 Sprint4 후반에 처음 이어진다. Sprint4는 -176부터 시작한다.
- 각 도메인 담당자는 조회 쿼리마다 프로젝트 조건을 넣어야 하고, PR 리뷰 확인 항목이 하나 늘어난다(5-6).

## 3. 검토 방법

- **브랜치**: `docs/backend-auth-policy-S15P31A108-172`. PR은 Draft로 열어 둔다. Draft는 자동 병합 대상이 아니라서 확인자 전원이 보기 전에 병합되지 않는다.
- **동의**: 2절 해당 행의 "확인" 칸에 `이름 ✔ 날짜`를 적어 커밋한다.
- **수정**: 본문을 직접 고친다. 고친 문장 끝에 `[수정: 이름]`을 붙이고, 커밋 메시지에 절 번호와 이유를 쓴다. 예: `docs: 5-2 6단계 수정 — TASK_OWNER는 서비스에서 검사 (S15P31A108-172)`.
- **반대**: 해당 문장 바로 아래에 `> 이견(이름): 이유 / 대안`을 남기고, 2절 해당 행 "확인" 칸에 `이름 ✖`를 적는다.
- **충돌 방지**: 고치기 전에 `git pull`, 커밋은 절 하나 단위로 작게 한다. 같은 행을 두 사람이 고쳐 충돌이 나면 나중에 푸시하는 사람이 합친다.
- **확정**: 확인자가 모두 ✔한 행은 작성자가 [확정]으로 바꾼다. 마감(10-28)까지 이견이 남은 행은 다음 팀 회의에서 정한다.
- **마무리**: 전 행이 [확정] 또는 [미결정]이 되면 상태를 "확정"으로 바꾸고 Draft를 해제한다. 확정 규칙 중 API 계약에 해당하는 것은 API Common 2절에도 옮긴다(5-9).

### 4-2. 순서에서 짚을 점

1. **0단계가 병목이 될 수 있다.** -156(작업 계획)은 이미 진행 중인데, 실제 권한 검사는 -170·-174가 끝나야 생긴다.
   **[제안]** -170 첫 PR(목표 10-28)에서 접근 검사의 호출 방법(5-6)과 테스트용 구현을 먼저 dev에 올린다. 다른 BE는 그 메서드로 개발하고, 실제 세션 연결은 뒤따라 붙인다. 업무 코드는 바꾸지 않아도 된다. 이 PR이 늦어지면 늦어진 만큼 -156·-192가 권한 검사 없이 진행되고, 나중에 붙이는 비용이 커진다.
2. **겹쳐 진행하는 단계는 계약부터 고정한다.** Sprint3에 1단계(문서·작업)와 3단계 일부(분석 -184, 검색 -129~-130)가 함께 있다. 서로의 입출력이 먼저 정해져야 병렬로 진행할 수 있다. 이미 있는 계약 티켓은 -107(AI 검증 입출력·실패 응답), -166(MCP 호출용 작업 서비스 계약), -180(알림·타임라인 이벤트 계약)이다.
3. **MCP 도구 연결(-176~-179)이 Sprint4에 몰려 있다.** **[제안]** Sprint4는 -176(MCP 공통 요청 처리)부터 시작한다. 그래야 각 도메인 담당자가 자기 도구를 붙일 시간이 남는다.
4. 저장소·PR·개인 대화 수집은 선행 과제로 두지 않는다 **[확정]**(POL-12, GIT-01~06 확장 확정).

### 4-3. 단계 완료 기준 [제안]

POL-12가 팀 결정으로 남긴 "단계별 완료 기준"의 안이다. 다음 단계 담당자가 **기다리지 않고 이어서 작업할 수 있는 시점**을 완료로 본다. 앞 단계의 다른 담당 작업이 덜 끝났으면 테스트용 데이터나 대역으로 확인해도 완료로 본다.

| 단계 | 완료 기준 |
| --- | --- |
| 0 | 로그인한 사용자가 프로젝트를 만들고 팀원을 초대·수락할 수 있다. 다른 BE가 접근 검사를 호출하는 예시와 테스트가 dev에 있다 |
| 1 | 승인된 기준 설계를 조회하고, 그 설계 항목 버전을 참조하는 작업 계획을 저장할 수 있다. 승인 기능이 아직이면 승인 설계를 테스트 데이터로 넣어 확인한다 |
| 2 | 검증 결과 4종(입력 부족 NEEDS_INPUT · 사람 검토 필요 NEEDS_REVIEW · 통과 PASS · 오류 ERROR)이 각각 테스트로 재현된다. 같은 작업을 두 번 시작할 수 없다. AI 경로는 `AiClient` 대역(시간 초과·실패 응답)으로 재현한다 |
| 3 | 로컬 Claude Code가 토큰으로 연결해 계획 등록 → 검증(비동기) → 시작 보고까지 끝낸다 |
| 4 | 설계 변경 승인 한 건이 "기존 검증은 다시 검증 필요(STALE), 진행 작업은 대기(WAITING)" → 알림 → 타임라인까지 이어진다 |
| 5 | POL-14 시나리오와 AC 인수 항목의 결과표가 나온다 |

## 5. 접근 거부 기준 (AC-10)

AC-10의 세 상황(다른 프로젝트의 Task, 다른 프로젝트의 contextId, 개인 원문 조회)을 구현 규칙으로 정리한다.

### 5-1. 이미 확정된 규칙

| 규칙 | 근거 |
| --- | --- |
| 다른 프로젝트 객체는 존재를 드러내지 않는 404로 거부 | API Common 2절 |
| `X-Project-Id`는 권한 근거가 아니다. 프로젝트 경로·객체 소속·토큰 범위를 서버에서 대조 | API Common 2절 |
| MCP의 프로젝트는 토큰에서 결정. 인자 `project_id`는 같은지만 확인 | MCP Tools "연결과 인증" |
| 에이전트 호출마다 토큰 폐기·현재 멤버십·객체 소속 확인 | MCP Tools "연결과 인증", 명세 MCP-08·AGT-02 |
| 권한·프로젝트 필터는 페이지·검색·집계 **전에** 적용 | API Common 3절 "페이지" |
| PRIVATE 기록은 작성자에게만 보인다. 요약·개수에도 같은 권한. 권한 없는 PRIVATE는 not_found | Backend REST CTX 절, MCP Tools MCP-06 처리 규칙 |
| AI 서버 입력에는 backend가 권한 검사한 원문·항목·작업만 넣는다 | AI Internal 공통 규칙 |
| 프로젝트 삭제(soft delete) 시 멤버·에이전트의 일반 접근 차단 | Backend REST PRJ-A05 |
| 멤버십이 끝나면(제외·나가기) 기존 토큰은 즉시 사용할 수 없다. 탈퇴 시 토큰 전부 폐기·세션 종료 | Backend REST MEM-A09·MEM-A10·ACC-A10 |
| 팀장 토큰으로 접속한 에이전트도 사람 승인·발행 API 불가 | API Common 2절 |
| 프로젝트 간 검색 금지. 비밀번호·토큰·환경 변수 원문·에이전트 내부 추론은 기록하지 않음 | 명세 POL-03 |

문서 반영이 필요한 곳: Backend REST CTX-A03은 "작성자만 허용"이라고만 적고 응답 코드가 없다. MCP-06은 404 메시지가 두 가지다. 2절 15번 행으로 정리한다.

### 5-2. 판정 순서 [제안]

모든 REST·MCP 요청을 아래 순서로 검사하고 **처음 걸린 단계의 결과**를 돌려준다. 순서를 고정해야 같은 상황이 API마다 다른 코드로 나오지 않는다.

| 순서 | 검사 | 실패 시 |
| --- | --- | --- |
| 1 | 인증: 세션 없음·만료, 토큰 없음·폐기, 경로에 맞지 않는 인증 수단(예: 에이전트 토큰으로 `/api/**` 호출) | 401 `unauthenticated` / `token_revoked` |
| 2 | 프로젝트 결정(아래 규칙) | — |
| 3 | 프로젝트 접근: 프로젝트가 없거나 삭제됨, 호출자가 활성 멤버가 아님 | 404 `not_found` |
| 4 | 객체 소속: 경로·단건 대상 객체의 프로젝트가 2에서 정한 프로젝트와 다름. MCP 인자 `project_id`가 토큰 프로젝트와 다른 경우 포함 | 404 `not_found` |
| 5 | 공개 범위: PRIVATE 기록인데 작성자가 아님 | 404 `not_found` |
| 6 | 역할·소유: 팀장(LEADER), 작업 담당자(TASK_OWNER), 기록 작성자(RECORD_AUTHOR, 수정 시) 조건 미충족 | 403 `forbidden` |

**프로젝트 결정 규칙(2단계)**

- `/api/projects/{id}/**`: 경로의 `{id}`.
- `/mcp`: 토큰의 프로젝트.
- `/api/human/**`처럼 경로에 프로젝트가 없는 API: 경로에 대상 객체가 있으면 **그 객체의 프로젝트**로 정한다. 본문 `project_id`가 이와 다르면 404다. 경로에 대상 객체가 없는 `POST /api/human/baselines`만 본문 `project_id`로 정하고, 3단계 검사를 그대로 받는다.

**목록·검색 필터 규칙**

- 4단계 소속 검사는 경로나 단건 대상의 ID에만 적용한다.
- 목록·검색의 필터 ID(예: `find_context`, 작업 기록 검색의 `task_id`)는 소속 검사를 따로 하지 않고 프로젝트 조건과 함께(AND) 쿼리에 넣는다. 다른 프로젝트 ID를 넣으면 오류 없이 0건이다.
- 검색어는 검색 범위를 바꾸지 않는다.

3·4·5단계를 모두 404로 묶는 이유: 이 단계에서 걸린 호출자는 대상이 있는지조차 알면 안 된다. 6단계까지 온 호출자는 같은 프로젝트 멤버이고 객체를 볼 수 있으므로 403이 정보를 새지 않는다.

각 행이 그대로 인수 시나리오 후보가 된다(→ -208).

| --- | --- | --- | --- |

| 2 | A 토큰으로 `read_context`에 B의 `contextId` 전달 | 도구 실패 `not_found`, 감사 기록 남김 | [확정] |

| 9 | 제외·나가기 직후 그 사람의 A 토큰으로 MCP 호출 | 401 `token_revoked` | [확정](차단), 응답 코드는 [제안] |
| 10 | 팀장 위임 직후 이전 팀장이 승인 요청 | 403 | [제안] |

### 5-4. 권한 회수 [제안]

- **반영 시점**: 다음 요청부터. 세션에는 계정 ID만 두고, 멤버십·역할은 매 요청 `project_member`에서 조회한다. 비용은 요청당 조회 1건이고 `UNIQUE (project_id, account_id)` 인덱스가 이미 있다.
- **캐시 없음**: MVP에서는 멤버십 캐시를 두지 않는다. 캐시를 두면 그 만료 시간만큼 회수가 늦어진다.
- **토큰 폐기**: 멤버십이 끝나는 모든 경로(제외 MEM-A09, 나가기 MEM-A10, 탈퇴 ACC-A10)와 프로젝트 삭제(PRJ-A05)는 같은 트랜잭션에서 그 프로젝트 토큰의 `revoked_at`을 채운다. 그래서 MCP는 401 `token_revoked`, 세션은 404가 된다. 폐기가 빠지는 경우를 대비해 3단계 멤버십 검사는 그대로 둔다.
- **비동기 작업**: 검증 워커 같은 비동기 작업은 접수 시점의 권한으로 실행을 마치고 결과를 저장한다. 그 결과를 쓰는 다음 요청(작업 시작 등)에서 권한을 다시 검사한다. 시작·재개·발행은 프로젝트 잠금 아래에서 멤버십도 다시 검사한다(API Common 5절).

### 5-5. 응답과 기록 [제안]

- 404 응답은 "없음"과 "접근 불가"를 구분하는 문구를 쓰지 않는다(5-3의 12행). 메시지는 "리소스를 찾을 수 없습니다" 하나로 통일한다.
- 실제 거부 사유(`cross_project`, `not_member`, `private_record` 등)는 서버 로그와 MCP 감사 기록에 남긴다. 인수 검증과 디버깅에 필요하다. 토큰·비밀번호·원문은 기록하지 않는다.
- 현재 `mcp_audit_log.result`는 `OK|DENIED|ERROR`뿐이고 사유 칸이 없다. `deny_reason TEXT`를 추가하는 마이그레이션을 -178(에이전트 연결·인증)에 포함하고, 그 전에는 서버 로그에만 남긴다. 없는 객체와 소속 불일치는 모두 `DENIED`로 기록한다.

### 5-6. 구현 위치 [제안]

BE 구현 세부다. 다른 파트는 건너뛰어도 된다.

| 검사 | 위치 | 담당 |
| --- | --- | --- |
| 1 인증 | Spring Security 필터 체인 둘: `/api/**`는 세션, `/mcp`는 Bearer 토큰 | 전진(-170·-178) |
| 2·3 프로젝트 접근, 6 중 LEADER | 공통 접근 검사(아래) | 전진(-170) |
| 4 객체 소속 | 각 도메인 저장소. **ID와 프로젝트 ID를 함께 조건으로** 조회한다. ID로 먼저 찾고 나중에 비교하지 않는다 | 각 도메인 담당 |
| 5 공개 범위 | 기록 조회·검색 쿼리의 조건 | 변준성(CTX) |
| 6 중 TASK_OWNER·RECORD_AUTHOR | 각 도메인 서비스 | 각 도메인 담당 |

**공통 접근 검사의 호출 방법(-170 첫 PR)**

- 각 도메인 서비스 메서드 첫 줄에서 `requireMember(projectId, 필요한 역할)`을 직접 호출한다.
- 반환값에는 `account_id`, `member_id`, `role`, 행위자 종류(사람·에이전트), 에이전트일 때 `agent_token_id`가 들어 있다. TASK_OWNER 판정(`task.assignee_member_id`)과 기록 작성자 저장(`context_record.author_token_id`)에 그대로 쓴다.
- 실패하면 기존 `ApiException`으로 404 `not_found` 또는 403 `forbidden`을 던진다.
- 테스트용 구현은 고정된 계정·멤버를 넣어 주는 테스트 설정이다.
- 이름·시그니처는 -170 PR에서 확정하고, 이 절은 그때 갱신한다.

**객체 소속 조회 예시**

- `project_id` 칸이 있는 테이블: `WHERE id = ? AND project_id = ?`.
- `project_id` 칸이 없는 테이블(`validation`, `task_plan_revision` 등): 소속 상위 객체와 조인한다. 예: `validation v JOIN task t ON t.id = v.task_id WHERE v.id = ? AND t.project_id = ?`.
- PR 리뷰에서 "프로젝트 조건 없는 ID 조회"를 확인 항목으로 둔다.

**벡터 검색**

- 검색은 backend가 `project_id`·공개 범위 조건을 쿼리에 넣어 실행한다. AI 서버는 backend가 넘긴 후보만 받고 DB를 직접 조회하지 않는다.
- 근사 검색 인덱스에 조건을 붙이면 결과가 요청한 개수보다 적게 나올 수 있다. 개수가 모자라면 범위를 넓혀 다시 찾거나 정확 검색으로 보충한다.

### 5-7. 다른 티켓과의 경계

- **개인 원문 공개 범위 자체**(무엇을 PRIVATE로 둘지, 수집 동의, 보관)는 -95·-110(박상은)이 정한다. 이 문서는 그 정책이 정해졌을 때 **어떻게 거부하는가**만 다룬다.
- 인수 기준 검증(테스트 작성·실행)은 -208에서 한다. 5-3 표가 입력이다.

### 5-8. 화면 처리 [미결정]

404·403을 받았을 때 화면에서 어떻게 안내할지(없는 페이지 안내, 권한 없음 안내, 목록으로 돌아가기 등)는 박민용이 정한다. 404는 "없음"과 "접근 불가"를 구분할 수 없다는 점(5-5)을 전제로 한다.

### 5-9. 확정 후 옮길 곳

확정된 규칙 중 API 계약에 해당하는 것(판정 순서, 프로젝트 결정 규칙, 필터 규칙, 토큰 폐기, 404 메시지)은 API Common 2절에 옮긴다. 구현자는 API 문서를 기준으로 보기 때문에, 이 문서에만 두면 기준이 두 곳으로 갈린다.
