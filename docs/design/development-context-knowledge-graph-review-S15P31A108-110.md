# #110 개발 컨텍스트 지식 그래프 관점 재검토

관련: [S15P31A108-110](https://ssafy.atlassian.net/browse/S15P31A108-110) · [S15P31A108-95](https://ssafy.atlassian.net/browse/S15P31A108-95) · [S15P31A108-131](https://ssafy.atlassian.net/browse/S15P31A108-131) · [S15P31A108-132](https://ssafy.atlassian.net/browse/S15P31A108-132) · 작성: 박상은 · **기준안 v0.4, 담당자 리뷰 전**

같이 볼 문서: [MVP 조회·공유 경계 검토안](development-context-mvp-boundary-S15P31A108-110.md)

프로젝트 개발 지식을 하나의 그래프로 연결하고 작업별로 탐색하며, 관계의 의미와 규칙을 이용해 간접 의존·변경 영향·충돌 후보를 추론하는 목표 구조를 기준으로 현재 설계를 대조한다. 기준은 GitHub dev `0af97f7`, ERD·V2~V5 migration, API·MCP 계약, Jira(2026-10-28 확인)다. **박상은 기준안은 MVP에서 규칙 추론 한 시나리오를 끝까지 검증한다. 담당자 리뷰 전 기준안이며 Jira 범위·구현·팀 합의를 확정하지 않는다.**

이 문서의 구분:

- **확인된 사실**: 코드·DDL·문서·Jira에서 직접 확인한 내용. 1절과 2절의 상태 열.
- **박상은 기준안**: 이 문서의 MVP 기준 방향이다. 다른 담당자 검토 전이며 확정된 Jira 요구사항이 아니다.
- **제안·합의 필요**: 기준안의 실현 방식과 타 담당 기능에 영향을 주는 세부 사항이다.
- **CDC 적용 방침**: 사용자가 팀에서 CDC를 적용하기로 했다고 전달했다. 기술 선택·운영 방식과 세부 범위는 미정이며 이 문서에서 CDC 구현이나 팀의 세부 합의를 확정하지 않는다.
- **담당자 의견**: 양지훈·변준성·오서현·전진의 전달받은 의견이다. 명시적으로 확인된 계약과 구분하며 다른 담당자의 수용·Jira 범위 변경을 의미하지 않는다.

검토한 티켓의 관계·영향 분석 요구와 사용자 목표를 대조한다. 특정 용어의 사용 여부만으로 관련 기능의 요구 여부를 판단하지 않는다.

후보만으로 승인 설계·작업 상태나 기존 게이트·무효화를 변경하지 않는다. 위 기준안은 관련 담당자의 리뷰를 받으며 Jira나 기존 계약은 이 문서로 변경되지 않는다.

## 0. 결론

**부분적으로 지원한다.** 데이터 모델의 방향은 맞지만, 그래프를 채우고 따라가는 부분이 대부분 비어 있다.

- **지원하는 부분.** PostgreSQL 스키마가 이미 종류가 정해진 관계 표(설계 항목·버전, 기준 설계, 작업 계획 참조, 작업 의존, 검증 참조, 변경 제안, 공유 기록 참조)로 작업·설계·검증·변경·기록을 **버전 단위**로 연결한다. 승인된 것과 AI 후보를 나누는 표시(`EXPLICIT`/`AI_CANDIDATE`, `ExplicitImpact`/`ImpactCandidate`)도 계약에 있다. 그래프 DB 없이 목표 구조를 표현할 수 있는 기반이다.
- **지원하지 않는 부분.**
  1. 검토 기준 dev `0af97f7`에서 설계 항목·기준 설계·의존 관계의 운영 쓰기 경로를 확인하지 못했다. #128은 보류됐다. 오서현님이 수동 입력·발행의 #194 구현을 설명했으므로 최신 반영 상태를 확인한다. 관계 확정 경로는 후속 제안이다.
  2. 설계 사이의 관계(`design_item_dependency`)가 종류·버전·승인 이력 없이 현재 값만 가진다. 과거 시점의 관계를 복원할 수 없다.
  3. 관계를 따라가는 조회는 "바뀐 항목 → 그 이전 버전을 계획에서 직접 참조한 작업" 1단계만 구현됐다. 의존 관계를 거친 영향 탐색, 작업 중심 서브그래프 조회는 없다.
  4. 화면 설계 전용 항목 종류가 없다. 기존 문서·요구사항으로 표현 가능한 범위와 별도 유형의 필요성은 확인해야 한다.
- **바꿀 것 (제안).**
  - 패킷을 "지식 저장소"가 아니라 "그래프 조회 결과의 표현 + 실행 시점 불변 기록"으로 정의한다.
  - 기존 관계 표들을 하나의 개념 스키마(노드·관계 목록)로 문서화한다.
  - #167 관계 조회를 서브그래프 조회의 기반으로 삼는다.
  - 의존 관계의 의미·승인·이력 규칙을 합의한다.
  - 정책 변경 → API → 작업의 간접 영향 후보를 계산하고 근거와 함께 MCP에 제공하는 규칙 하나를 MVP에 제안한다 (3.5절).
  - 승인 트랜잭션에서 기록한 변경을 CDC로 감지해 지식 표현·추론에 반영한다. 초기 적재·순서·재처리·일관성 등은 3.6절과 K12에서 결정한다.
  - 범용 edge 표나 그래프 DB는 MVP에 필요하지 않다.

## 2. 목표 구조와의 차이

### 2.1 노드

| 목표 노드 | 현재 표현 | 차이 |
| --- | --- | --- |
| 프로젝트 목표·요구사항 | 기획안 문서(PLAN), `design_item(kind=REQUIREMENT)` | 목표는 문서 원문으로만 존재 |
| 승인 설계 문서·항목 | `document_version`, `design_item_version`, `baseline` | 표는 있음, 생성 경로 없음 |
| API 명세·DB 스키마 | `API_CONTRACT`, `DATA_CONTRACT` 항목 + API_SPEC·ERD 문서 | 위와 같음 |
| 화면 설계 | 전용 UI·SCREEN kind 없음 (DOC-14 추가 첨부는 확장) | 기존 문서·요구사항으로 표현 가능한 범위와 전용 종류 필요성 확인 |
| 작업·계획 | `task`, `task_plan_revision` | 있음 |
| 담당 에이전트 | 담당 멤버·프로젝트 토큰·세션 | 실제 실행 에이전트의 식별·연결 기준은 별도 확인 필요 |
| 진행 상태·검증 | `task.status`, `validation` | 있음 |
| 공유 기록·의사결정 | `context_record` | 표는 있음. `DECISION`은 승인 설계가 아님 |
| 변경 이력·영향 | `change_proposal`, `approval`, `baseline` 연쇄 | 영향 결과 저장 표 없음 (#197) |

### 2.2 관계

| 목표 관계 (요청 예시) | 현재 표현 | 차이 |
| --- | --- | --- |
| 로그인 화면 작업 → 로그인 화면 설계 참조 | `task_plan_design_ref(READS)` | 화면 설계 전용 항목 종류가 없어 표현 방식 확인 필요 |
| 로그인 화면 작업 → 인증 API 의존 | `task_plan_design_ref(READS)` 직접 참조 | 계획이 직접 참조하면 표현 가능 |
| 인증 API → 인증 정책 참조 | `design_item_dependency` | 관계 종류가 없어 "참조"와 "의존"을 구분할 수 없음 |
| 인증 API → BE 인증 작업 | BE 작업의 `task_plan_design_ref(IMPLEMENTS)` | 있음 (역방향 조회) |
| BE 인증 작업 → 변경 기록 | `change_proposal.task_id`, `context_record.task_id` | 있음 |
| 인증 API 변경 → 영향받는 FE 작업 | `affected` SQL (직접 참조만) | 설계 의존을 거친 FE 작업은 찾지 못함 |

### 2.3 관계 메타데이터 (출처·승인·버전)

| 관계 | 출처 | 승인 여부 | 버전 |
| --- | --- | --- | --- |
| 작업 → 설계 | 작성 계정·토큰 (리비전) | 검증 PASS가 근거. 사람 승인은 없음 | 항목 버전 단위, 불변 |
| 설계 ↔ 설계 | `origin`, `confirmed_by/at` | `EXPLICIT`만으로 확정·승인을 보장하지 않음. 확인자·시각은 nullable이며 기준 발행·팀장 승인과 연결되지 않음 | **없음**. 항목 단위 현재 값. 변경 이력 없음 |
| 검증 → 설계 | 검증 실행 | — | 불변 스냅샷 |
| 변경 → 설계 | 제안자, `approval` | 팀장 승인 | 이전 버전 → 새 기준 |
| 공유 기록 → 설계 | 작성자 | 승인 아님 | 불변 |

가장 큰 공백은 **설계 ↔ 설계 관계가 승인·버전 체계 밖에 있다**는 점이다. 설계 항목 본문은 변경 제안 → 팀장 승인 → 기준 발행을 거치는데, 그 항목들 사이의 의존 관계는 같은 절차를 거치지 않는다. 그래서 "과거 AI가 참조한 의존 관계"는 검증 참조(`DEPENDENCY`)나 패킷에 스냅샷으로 남긴 경우에만 복원된다.

### 2.4 시나리오: 인증 API 응답 필드 변경

| 단계 | 계약·DDL | 구현 | 비고 |
| --- | --- | --- | --- |
| 1. BE 에이전트가 변경 제안 | MCP-04, `change_proposal(_item)` | 없음 (#195, MCP #179) | 제출만으로 설계·작업 상태가 바뀌지 않음 (MCP-04) |
| 2. 관련 설계·의존 확인 | CHG-A01 "명시 관계 영향 먼저", `design_item_dependency` | 없음 (#167, #197) | AI 영향은 별도 후보 (CHG-A05) |
| 3. 승인 시 새 설계 버전 | CHG-A09, 버전 불변 트리거, 기준 스냅샷 | 없음 (#198, #200) | 의존 관계는 새 기준에 포함되지 않음 |
| 4. 연결된 FE 작업 탐색 | `affected` | **직접 참조만 구현됨** (#164) | 의존을 거친 FE 작업은 빠짐 |
| 5. 영향 작업·담당 에이전트 식별 | `ExplicitImpact(task_id, member_id)`, NTF-02 | 담당 멤버 저장만 구현. 알림(#181) 없음 | 에이전트는 `get_design_changes`로 직접 확인 (NTF-04) |
| 6. 후속 컨텍스트에 최신 승인 반영 | MCP-01 "현재 승인 설계" | 컨텍스트 없음. 현재 버전 해석은 구현됨 | 패킷은 새로 만들고, 과거 패킷은 그대로 둔다 |
| 7. 과거 참조 버전·실행 컨텍스트 추적 | 계획 참조·검증 참조·패킷 불변, 조회 이력 | 계획 참조·조회 이력 구현됨 | 의존 관계의 과거 상태는 스냅샷이 없으면 복원 불가 |

AI 추정 관계 구분은 계약상 지켜진다. D5는 "AI 추론 관계는 무효화에서 제외", AI-A03은 "AI 결과는 자동 승인·작업 수정 근거가 아님", DesignDependency는 "AI 후보는 무효화 근거가 아님"으로 정해 두었다.

## 3. 아키텍처 제안 (제안)

### 3.1 기존 표를 그래프로 정의한다

새 저장소나 범용 edge 표를 만들지 않는다. 기존 표를 **종류가 정해진 관계형 그래프**로 보고, 노드·관계 목록과 각각의 권위 수준을 개념 스키마로 문서화한다.

| 권위 수준 | 해당 노드·관계 | 컨텍스트에서의 취급 |
| --- | --- | --- |
| A. 승인 기준 | 현재 기준의 설계 항목 버전·문서 버전 | 개발 판단의 근거 |
| B. 명시 관계 | `EXPLICIT` 의존, 계획 참조(READS·IMPLEMENTS·CHANGES), 작업 의존 | 권한·확정 조건을 검증한 탐색 경로. `EXPLICIT` 값만으로 승인 관계라 단정하지 않음 |
| C. 작업 상태 | 작업 상태·검증 상태·변경 제안 상태 | 현재 상황 정보. 설계가 아님 |
| D. 공유 기록 | `SHARED` 기록 | 동료가 남긴 데이터. 승인 설계가 아님 |
| E. 추론·AI 후보 | 규칙 영향 후보, `AI_CANDIDATE`, AI 영향 후보 | 출처·방법을 구분해 후보로 표시. 후보만으로 공식 설계·작업 상태나 무효화를 변경하지 않음 |
| 제외 | 타인의 `PRIVATE`, 다른 프로젝트, 미승인 초안 | 조회 결과에 노출하지 않음 (요약·건수 포함). 권한이 있는 과거 버전은 변경 근거·스냅샷에서 과거로 명시 |

### 3.2 네 가지 개념의 분리

| 개념 | 정의 | 저장 위치 | 현재 대응 |
| --- | --- | --- | --- |
| 지식 그래프 저장 | 위 표들. 계속 관리되는 원본 | 기존 표 | 일부 구현 |
| 컨텍스트 조회 | 작업을 기점으로 서브그래프를 탐색하는 BE 조회 서비스 | 저장 안 함 | 없음. #167이 기반 |
| 컨텍스트 패킷 | 조회 결과를 AI에게 주는 구조화 표현 (MCP-01 응답) | 응답 | #132 |
| 실행 스냅샷 | 실제 제공한 내용과 참조 버전의 불변 기록 | `dev_context_packet(_ref)` | DDL만 있음 |

`dev_context_packet`은 이미 "당시 패킷" 보존용(TRC-03, ERD)으로 설계돼 있다. 즉 기존 표의 역할은 **지식 저장소가 아니라 실행 스냅샷**이다. 지식 그래프 저장과 겹치지 않도록 다음 원칙을 제안한다.

- 설계 항목 버전·문서 버전·계획 리비전의 ID를 참조한다. 참조만으로 당시 AI에게 실제 전달한 발췌·요약·선택 결과를 재현할 수는 없다.
- 관련 작업 상태, 의존 관계, 추론 후보·경로·규칙, 검색 결과와 함께 **실제 전달한 payload**를 `content`에 보존한다. 저장 구조·내용은 합의 사항이다.
- `content_hash`는 실제 전달 payload 기준으로 계산한다. 같은 작업에 패킷이 여러 개 생겨도 원본 데이터 복제는 버전 노드 수만큼 늘지 않는다.

현재 DDL은 패킷 부모 행의 UPDATE만 차단한다. `dev_context_packet_ref`의 변경·삭제 방지와 프로젝트 정합은 별도 보강이 필요하다. 패킷 보존은 전달한 패킷의 추적이며 에이전트가 별도로 구성한 전체 프롬프트나 모델 응답까지 자동 재현한다는 뜻은 아니다.

### 3.3 작업 중심 서브그래프 조회 (BE 서비스)

`task_id`가 있을 때 (현재 계획 리비전 기점, 깊이 1 제안):

1. 현재 계획의 `task_plan_design_ref` → 참조 항목 버전. 현재 기준 버전과 비교해 최신 여부 표시 (구현된 `ProjectDesignLookup`·시작 게이트와 같은 규칙)
2. 그 항목의 명시 의존 1단계 (확정 조건을 확인하고 양 끝이 현재 기준에 있을 때만. `EXPLICIT` 값만으로 확정하지 않음)
3. 같은 항목을 참조하는 다른 작업의 ID·리비전·상태
4. 그 항목에 걸린 진행 중 변경 제안 (상태만)
5. 선택: 이 작업·항목을 참조하는 `SHARED` 기록 요약 (MCP-05~07 범위 결정 후, 기본 제외)

`task_id`가 없을 때는 연결된 관계가 없으므로 검색이 기점이다. 승인 설계 항목 매칭 + APPROVED 원문 검색으로 후보를 찾고, 그 후보에서 2~4를 확장한다. 이 결과는 **관계로 저장하지 않는다**. 계획 등록(`upsert_task_plan`)에서 에이전트가 참조를 명시해야 비로소 작업→설계 관계가 생긴다. 시작 허가·작업 생성은 기존 검증 절차만 한다.

권한은 그래프 탐색 단계마다 SQL 조건으로 건다 (프로젝트, 현재 기준, `SHARED OR 작성자 본인`). 탐색 후 필터로 대체하지 않는다 (05 문서 합의 5번).

### 3.4 관계를 만드는 시점

| 관계 | 생성 주체·시점 | 상태 |
| --- | --- | --- |
| 작업 → 설계 | 계획 등록·수정 때 에이전트·사람이 명시 | 구현됨 |
| 작업 → 설계 추천 | TRC-04 AI 추천 → 담당자 확정 시 새 리비전 (CTX-A05, #185, #151) | 계약만 있음 |
| 설계 ↔ 설계 (명시) | 변준성님: 최초 발행 전 초안 검토, 발행 후 관계 추가·삭제를 변경 제안으로 처리하고 팀장이 확정 제안. 오서현님: 최초 발행·변경 제안 진입점을 맡고 변준성님 저장 서비스를 같은 트랜잭션에서 호출 제안 | 양 담당자 서비스 경계·이력·승인 및 계약 반영 합의 필요 (K2) |
| 설계 ↔ 설계 (AI 후보) | #167 "AI 추천 관계는 후보로 구분 저장". 후보를 **생성**하는 AI 티켓은 없음 | 확장 제안 (5절) |
| 변경 → 영향 | 명시 관계 우선 (BE), AI 후보 별도 (#188, #197) | 계약만 있음 |

### 3.5 MVP 규칙 추론 시나리오 (박상은 기준안, 담당자 리뷰 전)

**기준안:** 수동으로 확인한 관계를 바탕으로 정책 변경의 간접 영향 후보를 계산하고, 근거를 저장해 MCP 컨텍스트에 전달한다. 이 규칙 하나가 실제로 동작하는 것을 MVP에서 검증한다. 범용 추론 엔진이나 #128 자동 추출을 선행하지 않는다.

#### 관계 구축과 변경

1. 사람이 PLN-A07 수동 입력 경로로 인증 정책 `P v1`과 로그인 API `A v1`을 등록한다. 문서 버전·원문 위치를 기록할 수 있다. 오서현님은 #194 수동 등록·수정·제외 및 발행 구현을 설명했다. 검토 기준 dev `0af97f7`에서는 확인되지 않아 최신 반영 상태를 따로 확인한다.
2. 기존 PLN-A10 최초 기준 설계 발행 요건에 따라 항목과 문서를 승인하고 기준 `B1`을 발행한다. 필수 문서·분석 상태·검토 해시 등 기존 검증을 생략하지 않는다.
3. 최초 발행 전에는 관계를 초안으로 함께 검토하고 팀장이 `A DEPENDS_ON P`를 확정한다는 담당자 제안이다. 관계 리비전·근거와 검토 스냅샷·리비전 해시에 관계를 포함하는 방식은 합의한다. 관계 입력은 #194 병합 후 후속으로 제안됐으며, `EXPLICIT` 값 자체는 승인 증거가 아니다.
4. FE 작업 `T`의 현재 계획 리비전이 `A v1`을 `READS` 또는 `IMPLEMENTS`로 참조한다. 작업 계획 참조는 기존 저장 기능을 사용한다.
5. 인증 정책 변경 제안이 기존 승인 절차로 발행되어 `P v2`, 기준 `B2`가 된다. 관계를 자동 해제하지 않고 **재확인 필요**로 표시한 뒤 팀장이 유지·해제한다. **박상은 기준안:** 재확인 전에는 이 관계를 규칙의 확정 근거로 사용하지 않고 분석 대기로 표시한다. 대기는 영향 0건이 아니다. 승인 트랜잭션의 표시와 유지·해제 경로는 BE 담당자 리뷰가 필요하다.

PLN-A07·PLN-A10의 수동 항목 경로는 #194 담당자 구현 보고와 기준 dev의 확인 결과를 구분한다. 관계 입력은 #194 범위 밖의 후속 제안이고 변경 제안의 관계 연산도 계약 반영이 제안됐다. fixture·SQL seed는 실제 등록→승인→조회 경로를 대체하지 않는다.

#### 규칙과 결과

**`POLICY_API_TASK_IMPACT` v1 (박상은 기준안):** 승인된 정책 `P`의 변경 전·후 버전과 분석 기준이 있고, 확정된 `API A DEPENDS_ON P` 및 현재 작업 계획 `T READS/IMPLEMENTS A`가 같은 프로젝트에서 유효하면 `T`에 대한 **간접 변경 영향 후보**를 만든다. 관계 의미와 방향은 `A → P`, `T → A`이며 변경에서의 역방향 탐색 경로는 `P ← A ← T`다. 임의 관계의 전이성을 일반화하지 않는다.

결과의 `검토 필요`는 **추론 후보 상태**이며 validation의 `NEEDS_REVIEW`나 task의 `WAITING`이 아니다. 규칙·AI 후보만으로 공식 관계를 승인하거나 기존 직접 참조 기반 `STALE`, `WAITING`, 시작 게이트를 변경하지 않는다. AI-A02 후보는 별도 기존 검증 계약에 따라 BE의 검사·판정에 활용될 수 있다.

| 후보 근거 | API 버전, 관계 리비전·방향, 작업 계획 참조, 각 경로. 중복 작업은 묶되 경로는 보존 |
| 검토·전달 | 후보 검토 이력과 실제 전달한 승인 설계·후보·경로·규칙·버전·payload·해시 |

이는 논리 모델 제안이며 테이블·DTO를 확정한 것은 아니다. 전진님은 관계 원본의 `origin=EXPLICIT/AI_CANDIDATE`를 유지하고 **응답 후보 출처만** `candidate_origin=RULE/AI_CANDIDATE`로 분리할 것을 제안했다. 오서현님은 #197의 영향 분석 결과에 규칙 후보·경로를 저장할 수 있다고 설명했다. 이는 규칙 후보를 확정 관계로 저장한다는 뜻이 아니며, 별도 후보 저장 구조의 마이그레이션 필요 여부는 설계에 달렸다. 관계 리비전·당시 확정/재확인 상태 없이는 항목 버전 ID만으로 과거 관계를 복원할 수 없다. 발행 당시 이력·스냅샷이 없으면 분석 시점 관계라고 명시한다.

기준 발행 후 분석을 접수·재시도하는 방식과 유실 방지·중복 방지는 BE 합의 사항이다. 분석 중 기준·관계·계획이 바뀌면 입력 리비전을 고정하고 현재성 재확인 또는 재분석한다. 실패·권한 부족·재확인 대기를 **영향 없음**으로 표시하지 않는다. 조회·추론 입력부터 프로젝트·승인·공유 권한을 적용하며, 권한 없는 노드가 후보의 경로나 요약으로도 노출되지 않도록 한다.

AI-A02는 계획 충돌 finding 후보, AI-A03은 의미적 변경 영향 후보를 담당하는 계약 초안이다. **박상은 기준안:** 규칙이 후보·연결 경로를 찾고 #188 AI가 변경 내용·관련 문서를 비교해 영향 가능성을 설명한다. 관계 경로·문서 출처와 AI 해석은 분리하고, 근거 부족 시 확인 필요로 남기며 AI 실패 시 규칙 후보는 보존한다. 규칙 후보를 AI-A03 입력으로 넘기려면 계약 변경이 필요하며 양지훈님·오서현님 리뷰가 필요하다. Jira #188·#197은 MVP로 기재되어 있으므로 기존 확장 보류 합의의 적용 범위를 확인한다.

### 3.6 CDC 적용 방침과 미결 설계

**전달된 방침:** 온톨로지화에 CDC(Change Data Capture)를 적용한다. 구체적인 CDC 도구·전송 방식·별도 저장소 도입·운영 담당·구현 상태는 확정되지 않았다. 검토 기준 코드에서 CDC 구현은 확인하지 못했다.

```text
사람의 검토·승인 및 관계 변경 / 설계 발행 (원본 DB 트랜잭션)
    → 커밋된 변경을 CDC로 감지
    → 권한·승인·버전 규칙을 적용해 프로젝트 지식 표현 동기화
    → 규칙 영향 후보 계산·#197 분석 결과 보존
    → 권한을 검사해 MCP 후보·근거 전달 및 실제 payload 스냅샷
```

기존 PostgreSQL의 항목·관계·기준이 원본이다. CDC는 변경을 전달하며 관계 의미 추출, 팀장 승인, 기존 게이트·무효화 결정을 대신하지 않는다. 지식 표현은 기존 테이블을 이용한 조회 모델이나 별도 파생 모델 중 합의하며 별도 그래프 DB를 전제하지 않는다. 발행 및 직접 무효화의 기존 원자적 트랜잭션과, 관계 등록 서비스·재확인 표시를 동일 트랜잭션에서 호출하자는 오서현님 제안을 유지한다. CDC는 커밋 이후를 처리한다.

CDC 초기 데이터 적재와 시작 지점의 일관성, 트랜잭션 단위 원자성·프로젝트별 순서, 중복·멱등성·checkpoint·재처리, 삭제·스키마 변경, 장애 복구·재구축·지연 모니터링, 권한·민감 데이터 최소화, 이벤트와 분석 실행의 연결은 **모두 미결**이다. 후보·감사 기록 등 CDC 산출물이 다시 원본 갱신으로 반복되지 않도록 캡처 범위·쓰기 소유권도 정해야 한다. 파생 모델이 뒤처지거나 기준·관계 버전이 불일치할 때 이를 영향 0건으로 반환하지 않고 대기·오류·미평가를 표시한다. 기존 설계의 브로커 없음 방침 및 이벤트 유실 방지 Q03과 CDC 도입의 관계도 확인한다. 실시간 전달이나 정확히 한 번 처리를 이미 보장한다고 가정하지 않는다.

### 3.7 전달받은 담당자 의견 (제안, 범위·계약 미확정)

| 담당자 | 전달받은 의견 | 추가 확인 |
| --- | --- | --- |
| 변준성 | 관계 초안은 최초 발행 시 검토, 이후 추가·삭제는 변경 제안으로 팀장이 확정. 관계의 출처·이유·경로·버전·확정 이력을 누적. 새 설계 버전에서 기존 관계는 자동 해제하지 않고 재확인 필요. 확정 관계를 따라간 결과는 후보이며 무효화 근거가 아님 | 관계 조회 응답 모양 공유 예정. 재확인 필요 관계의 후보 사용과 Q02 후보·판정 깊이 별도 결정 |
| 오서현 | #194에서 사람의 5종 항목 등록·수정·제외와 팀장 발행 구현을 설명. 발행은 필수 문서 4종 색인 완료와 설계 항목 1개 이상 필요. 관계 진입점(초안·변경 제안)은 본인이, 저장·이력·조회·규칙 계산은 변준성님이 맡도록 제안. 같은 승인 트랜잭션에서 저장 서비스를 호출하고 검토 스냅샷·리비전 해시에 관계 포함. 최초 발행 관계 입력은 #194 병합 후 후속 제안 | #194 최신 브랜치·병합 상태, 제안한 담당 분담·동일 트랜잭션 인터페이스와 변경 제안 계약 확인 |
| 오서현 (#197) | 규칙·AI 후보를 분석 결과에 저장하고 출처, 규칙 ID·버전, 항목 버전별 경로, 관계 확정/재확인 상태, 사유를 기록. 규칙 버전은 영향 입력 해시에 포함하며 오래된 결과 표시. 분석 대기와 0건 구분. AI 실패에도 명시 영향·규칙 후보 보존 | 관계 리비전·task/plan ID 및 이벤트·분석 스냅샷, AI-A03 입력 계약 변경, 저장 스키마 확정 |

| 전진 | MCP-01 `design_items`는 승인 설계만, `impact_candidates`는 후보 별도. 응답 후보의 `candidate_origin=RULE/AI_CANDIDATE`와 규칙·경로·사유를 구분. 전체 전달 payload·해시 보존, ref는 승인 항목만, 후보 조회용 구조는 별도 제안 | 응답·권한·보존 세부 및 #197 저장 모델, #131·#132 계약 변경 합의 |

전진님의 후보 응답 제안은 대상 설계 버전 ID·key, `candidate_origin`, 규칙 ID·버전, 항목 버전과 관계를 잇는 경로, 사유, `status=CANDIDATE`를 포함한다. 규칙 집합 버전은 MVP에서 코드 상수로 두는 안이다. AI 후보는 규칙 ID가 없을 수 있으므로 출처별 필수 필드를 별도로 결정한다.

추가 추천: 후보는 명시 관계 2단계와 합의한 규칙 매칭까지, 최대 10개. 짧은 경로 → 진행 중인 다른 작업의 참조 → API/DATA 계약 순으로 정렬하고 `candidates_truncated`로 잘린 개수를 표시한다. 게이트·무효화는 명시 관계 1단계 제안이다. **둘 다 Q02 미결**이며 설계 간 edge와 작업→설계 참조를 깊이에 어떻게 셀지부터 정한다. 현재 D5의 직접 참조 무효화가 1단계 확장으로 이미 변경된 것은 아니다. 동일 필드 참조 규칙을 이번 한 시나리오에 포함할지도 합의 전이다.

전진님은 후보를 `task_plan_design_ref`에 넣지 않고 계획 `unlinked`에 확인 필요 내용으로 기재, 팀장 승인된 변경 제안으로 확정 관계에 반영하는 방향도 제안했다. `constraints`의 후보 안내 고정 문구는 승인 설계의 제약과 구분해 출처·의미를 결정한다. 후보는 작업 대상인 경우 `task_id`·계획 리비전도 필요하며, 분석 대기·실패·잘림을 빈 후보와 구분한다.

프로젝트 멤버의 패킷 열람, 에이전트 토큰의 프로젝트·과거 패킷 범위, 탈퇴·폐기 시 차단과 메타데이터만 기록하는 감사 정책은 전진님 제안이다. 실제 권한 범위는 개인·민감 정보와 함께 합의한다. payload 전체 저장을 택할 경우 전달된 원문 발췌도 저장되므로 원문 전체를 제외하는 정책과 실제 전송·보존 범위를 맞춘다. 검증 재사용 해시에 규칙 버전을 넣자는 제안은 어떤 검증이 해당 규칙에 실제로 의존하는지와 무효화 범위부터 결정한다. 측정용 후보 조회 구조 및 H1 지표는 별도 합의 사항이다.

MVP에서 "이미 관계로 연결된 지식"이 실제로 존재하려면 **설계 항목이 입력돼야** 한다. #128이 빠진 지금은 설계 항목이 비어 있을 수 있고, 그러면 컨텍스트는 관계가 없는 원문 청크 검색에 의존한다. 원문 청크는 문서 버전에만 연결돼 있고 설계 항목·작업과 관계가 없다. 이것이 목표 구조와 MVP 사이의 가장 큰 현실적 차이다 (K3).

## 9. 기존 MVP 경계 검토안과의 정합성

경계 검토안에도 패킷 정의, B0·B5·B6·B8과 3.5절 연계를 제안으로 반영했다. 아래 사항의 세부 문구·범위와 실제 계약이나 Jira 변경은 별도 합의가 필요하다.

1. 2절 표 앞에 "패킷 = 서브그래프 조회 결과의 표현, 저장 시 실행 스냅샷"이라는 정의를 넣는다 (이 문서 3.2).
2. B0에서 MCP-01·TRC-03의 기본 스냅샷 계약과 #90의 확장 제외 범위를 구분한다.
3. 2절 출처 표에 "권위 수준" 열을 이 문서 3.1의 A~E로 맞춘다.
4. 5절 #131 입력을 "BE가 조회한 작업 중심 서브그래프 + 검색 결과"로 다시 쓰고, 탐색과 선택의 담당 구분을 명시한다.
5. 4절 합의 항목에 K2(설계 의존 규칙), K4(영향 범위), K5(검증 의존 참조)를 추가하거나 이 문서를 링크한다.
6. 3.5절의 한 가지 규칙·후보 전달은 **박상은 MVP 기준안**으로 표시하고 담당자 합의 전 현재 #131·#132 요구로 단정하지 않는다.
