# 작업 계획 검증과 검색 현황 (#184)

기준: 184번 브랜치 시작 시점의 `origin/dev`. 기능 존재 여부와 실제 연결 여부를 구분한다.

## 이미 있는 부분

- 작업계획은 `TaskPlanInput`의 구조화 필드와 `design_refs`로 등록하고 리비전으로 저장한다. 서버는 같은 프로젝트의 현재 기준 설계 항목과 버전을 확인한다.
- 승인 문서의 정규화·청킹·임베딩·`document_chunk` 색인 작업과 문서 검색 API의 `KEYWORD`, `SEMANTIC` 모드가 있다.
- 키워드 검색은 현재 기준의 문서와 설계 항목을 대상으로 한다. 벡터 검색은 문서 청크를 반환한다. 문서 청크가 설계 항목이나 작업과 일대일로 연결된다고 가정할 수 없다.
- AI 공통 LLM 클라이언트와 검증 내부 API AI-A02의 입출력 계약이 있다.

## 현재 브랜치에 추가된 실행 흐름

1. #159의 `POST /api/projects/{project_id}/tasks/{task_id}/validations`가 요청자 권한과 작업 소유권·기준 버전을 확인해 접수한다. 규칙만으로 판정할 수 없으면 실행과 작업을 큐에 넣고 GET으로 조회한다. 동일 검증 재시도와 REST 멱등성 변경은 #161 범위다.
2. #159 단일 워커가 run과 lease를 확보하고 명시적 규칙을 재검사한다. 차단 규칙이 있으면 AI 호출 없이 RULE finding을 저장한다.
3. 워커는 작업계획 제목·목표·범위·API 경로로 키워드와 벡터 검색을 수행하고, 관련 작업과 승인 설계를 모아 `/v1/validate`로 전달한다. 명시 참조와 검색 후보를 구분한다.
4. BE가 모델 응답의 검사 범위·출처·ID와 현재 기준·계획·lease를 재확인한 뒤 결과와 사용량을 원자적으로 저장한다. 실패 시 ERROR finding, 만료 시 RETRY, PARTIAL은 HUMAN_REVIEW로 기록한다.
5. 검색 권한은 접수한 요청자의 계정과 에이전트 토큰을 다시 확인한다. 요청자 정보는 서버 내부 실행 정보이며 공개 조회 응답에 넣지 않는다. 이전에 접수되어 요청자 정보가 없는 작업은 검색하지 않고 실패로 종료한다.

`VALIDATION_WORKER_ENABLED`로 워커 자동 실행을 설정하며 기본값은 `true`다. AI 연결에는 `AI_BASE_URL`, 일치하는 `AI_INTERNAL_TOKEN`, GMS 모델 설정이 필요하다. 벡터 검색을 위해 문서 색인과 임베딩 설정이 준비돼야 한다. 격리 PostgreSQL과 테스트용 OpenAI를 연결한 네 합성 사례는 통과했다. 검색 임베딩은 합성 벡터를 사용했으며 운영 GMS·실제 임베딩 모델 및 PostgreSQL 동시 경합은 아직 검증하지 않았다. 상세 결과는 `ai/evaluations/validation/results-db-e2e-2026-10-29.md`에 있다.

## 아직 남은 부분과 제한

- #159 접수 규칙에서 READS 참조만 있고 unlinked·기존 관련 작업이 없는 계획은 의미 분석 없이 즉시 PASS한다. 이 경로는 #184 검색이나 AI를 실행하지 않으며, READS 설계의 의미 불일치나 검색으로만 발견되는 관련 작업의 영향 검사는 포함하지 않는다. READS의 검사 범위 확대는 Q02 및 #159 담당자와 협의가 필요하다.
- 검색 후보는 확정 참조가 아니고 검색 결과 전체의 재현율을 보장하지 않는다. 문서 청크의 출처 문서가 같은 설계 항목은 후보로만 포함하며 임의의 원문 evidence로 연결하지 않는다.
- 작업계획 자체의 벡터 검색은 아직 없고 관련 작업은 현재 설계 참조·명시 의존성으로만 찾는다. 승인 설계의 원문 버전과 정확한 행 범위 및 전체 텍스트 해시가 확인되는 경우에만 evidence를 생성한다. 행 범위가 없으면 검증을 보류한다. 정책 부재의 확정과 계획 작성 전 `get_development_context` MCP 연동은 아직 미구현이다.
- 제한된 MVP에서 명시 설계 참조가 있고 `no_contract_change=true`, `CHANGES`·`unlinked`가 없으며, 미확인 검색 후보·근거 패킷이 없는 계획은 지정된 검사 완료 시 PASS할 수 있다. 검색·AI의 모든 필수 검사를 마치고, API 명세에는 요청 필드와 응답 구조가 있어야 한다. 검증 결과는 지정 범위에 한정되며 검색 전체의 재현율은 UNKNOWN이다.
- 그 밖의 구조화 계약 변경·미연결 내용, 미확인 후보, 미검증 근거 패킷, 검사 누락·검색 잘림 또는 불충분한 API 명세는 자동 PASS하지 않고 진단과 HUMAN_REVIEW로 남긴다. 근거 패킷의 제약 전체를 AI에 전달하는 계약, 후보 선정 기준과 정책 부재 확인 방식은 아직 협의가 필요하다.
- 관련 OPEN 질문은 검증 입력에 포함하고 결과 저장 전에 다시 조회한다. 질문 쓰기 경로와 프로젝트 잠금 순서에 대한 동시성 검증이 필요하다.
- 문서 벡터 검색의 현재 limit은 20개다. 검색 결과가 더 있거나 검색 질의 제한을 넘으면 검증은 보류되므로, 청크가 많은 정상 문서도 PASS하지 못할 수 있다. 상위 K개 검색의 의미·관련성 판정은 별도 계약 및 평가가 필요하다.
- 검색 진단의 공개 DTO 계약과 오류·실행 정책은 BE 담당자와 협의가 필요하다. 운영 GMS·실제 데이터·검색 품질 및 동시성 검증 전 운영 준비를 확정하지 않는다.

## 평가할 대표 사례

아래는 실행 결과가 아니라 테스트할 기대 동작이다. 실제 평가에서는 입력 스냅샷·검색 결과·모델·출력·실패 여부를 별도로 기록한다.

| 사례 | 입력 | 기대 결과 |
| --- | --- | --- |
| 정상 | 계획과 승인 API가 동일한 `memberId`를 사용 | 해당 검사에서 확인된 충돌 없음. 최종 PASS는 서버의 전체 판정에 따른다. |
| 명시적 불일치 | 승인 API는 `memberId`, 계획은 같은 위치에 `userId` 사용 | 두 내용을 비교한 불일치 후보와 승인 항목 근거를 반환한다. |
| 정책 근거 부족 | 계획에 권한 처리가 있으나 관련 정책을 찾지 못함 | 검색 실패만으로 정책 부재를 단정하지 않고 미검사·근거 부족으로 표시한다. |
| 근거 충돌 | 승인된 구조화 내용과 같은 항목의 원문에 서로 다른 내용이 있음 | 충돌을 설명하고 확인을 요청한다. 한쪽을 조용히 승인 내용으로 덮어쓰지 않는다. |
| 검색 장애 | 벡터 색인 미완료 또는 검색 호출 오류 | 결과 없음으로 바꾸지 않고 실행 오류로 처리한다. |
