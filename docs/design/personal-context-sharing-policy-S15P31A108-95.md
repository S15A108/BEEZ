**CTX-07~09·11·12 원문은 확인하지 못했다.** 저장소의 요구사항 명세서(`docs/beez-requirements-preflight.md`)에는 CTX-01~04만 있고, Notion 업무 분담안에도 ID와 "개인 맥락" 라벨만 있다. 이 문서는 Jira #95 작업 내용 5 "개인 맥락 저장·검색·계층 관리 검토"를 기준으로 판단했다. 원문을 확인한 뒤 4.4절을 보완한다.

관련 확정 사항 (재론하지 않음):

- 개인 기록은 명시적 제출, 수정은 새 리비전, 동시 수정 시 409, `kind=DECISION`은 승인 설계가 아니다 ([01 아키텍처](01-system-architecture.md) 컨텍스트 행, ERD `context_record`).
- 남의 PRIVATE 기록 조회는 403이 아니라 404이고, 검색 결과·건수에도 드러내지 않는다 ([05](05-build-order-and-access-policy.md), [06](06-project-access.md)).
- 감사 기록에는 인증정보·개인 대화 원문을 넣지 않는다 (MCP-09). MCP-01 감사에는 `request` 본문을 남기지 않는다 (#110 감사 기준안).
- 물리 삭제 없음, 기록 리비전은 트리거로 UPDATE 차단 (ERD 공통 규칙, `trg_context_record_immutable`).
- 공유 기록·개인 기록은 MCP-01 패킷에 넣지 않는다 (#110 2절 표).

## 2. POL-01 컨텍스트 분류와 근거 우선순위

[지식 그래프 재검토안](development-context-knowledge-graph-review-S15P31A108-110.md) 3.1절의 권위 수준을 그대로 쓴다. 새 분류를 만들지 않는다.

| 순위 | 분류 | 해당 데이터 | 컨텍스트에서의 취급 |
| --- | --- | --- | --- |
| A | 승인 기준 | 현재 기준(`project.current_baseline_id`)의 설계 항목 버전·문서 버전 | 개발 판단의 근거 |
| B | 명시 관계 | 확정 조건을 확인한 `EXPLICIT` 의존, 계획 참조, 작업 의존 | 탐색 경로. 관계 자체가 설계 내용은 아님 |
| C | 작업 상태 | 작업·검증·변경 제안 상태 | 현재 상황 정보 |
| D | 공유 기록 | `context_record` `SHARED` | 동료가 남긴 참고 정보 |
| E | 추론·AI 후보 | 규칙 영향 후보, `AI_CANDIDATE`, AI 영향 후보, 비비 답변 | 출처·방법을 붙인 후보 |
| 제외 | — | 타인의 PRIVATE, 다른 프로젝트, 미승인 초안 | 결과·요약·건수에 노출하지 않음 |

**충돌 규칙 (추천안):**

1. 하위 순위 근거는 상위 순위 근거를 덮어쓰지 않는다. 예: `DECISION` 기록이 "응답 필드를 `userId`로 바꾸기로 함"이라고 해도 승인된 API가 `memberId`면 승인 API가 기준이다.
2. 충돌을 발견하면 어느 쪽이 맞는지 AI가 정하지 않는다. 두 근거를 출처와 함께 `unresolved`(MCP-01) 또는 "정보 부족·검토 필요"(비비 답변)로 넘긴다 (POL-05, BEE-04).
3. 같은 순위끼리는 최신 리비전·최신 기준을 우선하되, 과거 근거는 "과거 버전"으로 표시해 남긴다 (`is_latest_revision`, `references_current`).
4. 요약에도 문서 ID·버전·항목 위치를 보존한다. 출처를 잃은 요약은 근거로 쓰지 않는다 (POL-01 원문).

**팀 결정 필요:** 컨텍스트 유형명을 위 A~E로 공통 문서에 둘지 (#110 K1과 같은 질문).

## 3. POL-02 조회 수준

**추천안: L0/L1/L2를 두지 않고 summary/detail 두 수준만 둔다.** 기존 도구 구분에 그대로 대응시켜 새 파라미터를 추가하지 않는다.

| 대상 | summary | detail |
| --- | --- | --- |
| 공유 기록 | `find_context` 목록의 `ContextRecordSummary` (요약·종류·작성자·리비전·최신 여부·참조 현재성) | `read_context(RECORD)`의 `ContextRecord` (상세·참조 버전·당시 계획·근거 패킷 추가) |
| 컨텍스트 패킷 | MCP-01 응답 자체가 작업 하나에 필요한 범위. 별도 요약 수준 없음 | `read_context(PACKET)` |
| 개인 원문 대화 | 제공하지 않음 | 제공하지 않음 |

- 두 수준 모두 출처(문서·버전·위치 또는 작성자·리비전)와 유효성(`is_latest_revision`, `references_current`)을 포함한다. 현재 스키마가 이미 충족한다.
- summary 길이 상한 (추천안): 공유 요약 `summary` 500자. `request`의 2,000 코드 포인트 상한(#110 기준안)과 같은 방식으로 초과 시 400 `validation_failed`, 잘라 저장하지 않는다. `detail`은 10,000자. 수치는 미결정이다.
- MCP-01 응답 크기 상한·잘림 처리는 #132에서 정한다. 이 문서는 "잘렸으면 잘린 사실과 전체 조회 경로를 표시한다"는 원칙만 둔다.

이 대응으로 #132가 기다리던 POL-02 결정은 풀린다. #132는 `summary`/`detail`을 별도 필드로 만들지 않고 위 대응을 따른다.

## 4. POL-03 개인 기록 수집과 공유 경계

| 대상 | 처리 | 상태 |

**공유 동의 (추천안):** 프로젝트 참여만으로 개인 기록 공유에 동의한 것으로 보지 않는다. 기록마다 `visibility`를 필수로 받는 현재 계약이 "기록 단위 동의"다. 기본값을 두지 않는다 (현재 `@NotNull`).

### 4.4 CTX-07~09·11·12 개인 맥락 저장·검색·계층 관리

**추천안: MVP에서 구현하지 않는다.** 근거:

- POL-12·13 추천: 사전 검증 파이프라인을 먼저 완성하고 전체 대화 분석·자동 기록은 효과 확인 후 판단한다.
- AC-01: 개인 작업 기록이 없는 첫 작업도 승인 설계와 계획만으로 패킷·검증·시작이 가능해야 한다. 개인 맥락은 MVP 흐름의 필수 입력이 아니다.

## 8. 발견한 불일치

담당 문서·코드라 이 문서에서는 고치지 않는다. 담당자 확인 후 반영한다.

1. **공유 철회가 되지 않는다.** `visibility`는 리비전마다 정해진다. SHARED rev1 뒤에 PRIVATE rev2를 추가하면, 다른 멤버에게는 rev2가 보이지 않으므로 `ContextLookup.superseded`가 rev1을 대체되지 않은 것으로 계산해 `is_latest_revision=true`로 보여준다. 작성자는 공유를 거둔 줄 알지만 동료에게는 rev1이 최신으로 남는다 (V7).
2. **PRIVATE 첫 리비전의 존재가 드러난다.** PRIVATE rev1 → SHARED rev2이면 다른 멤버는 rev2의 `root_id`(=rev1 ID)와 `revision_no=2`로 비공개 이전 판이 있다는 사실을 알 수 있다. 내용 노출은 아니며, 허용할지 확인이 필요하다.
3. **`find_context`가 이전 리비전도 반환한다.** 같은 기록의 여러 리비전이 검색 결과에 함께 나온다. `is_latest_revision`으로 구분은 되지만 기본값을 최신만으로 할지 정해야 한다 (Q10 "PRIVATE·리비전·패킷 검색").
4. **MCP-05·07 이름과 PRIVATE.** 도구명은 "공유 작업 기록"인데 PRIVATE 저장을 허용한다. 4.3절대로 PRIVATE를 "작성자 메모"로 유지한다면 도구 설명에 그 의미를 적는다.
