# #95 개인 맥락·공유 정책 검토안

관련: [S15P31A108-95](https://ssafy.atlassian.net/browse/S15P31A108-95) · 선행 검토: [S15P31A108-110](https://ssafy.atlassian.net/browse/S15P31A108-110) ([MVP 경계 검토안](development-context-mvp-boundary-S15P31A108-110.md), [지식 그래프 재검토안](development-context-knowledge-graph-review-S15P31A108-110.md)) · 이 결정을 쓰는 작업: [S15P31A108-132](https://ssafy.atlassian.net/browse/S15P31A108-132), [S15P31A108-135](https://ssafy.atlassian.net/browse/S15P31A108-135) · 작성: 박상은 · **검토안 v0.3, 담당자 확인 요청 중**

POL-01·02·03·14와 CTX-07~09·11·12를 검토해 수집·공유·접근·보존 범위의 결정안을 정리한다. Jira #95는 **검토 작업**이며, 이 문서가 개인 대화 수집이나 개인 맥락 저장 기능의 구현을 확정하지 않는다 (업무 분담안: "개인 맥락 검토 담당의 지정은 구현 확정을 의미하지 않는다").

**작성 방식:** 다른 담당자의 확인이 필요한 항목도 검토 담당인 박상은이 먼저 판단안과 근거를 적고, 해당 담당자에게 확인을 요청한다. 확인하는 사람은 빈칸을 채우지 않고 판단안에 동의·수정·반대로 답한다.

라벨:

- **확정** = 요구사항·기존 계약·팀 합의로 이미 정해짐
- **구현됨** = dev 코드에 있음
- **박상은 판단 · ○○ 확인 요청** = 이 문서의 판단안. 확인 전에는 기존 계약·Jira·코드가 바뀐 것으로 다루지 않는다

기준: dev `9f9af95` (2026-10-30), Jira 같은 날 조회.

**CTX-07~09·11·12 원문은 확인하지 못했다.** 저장소의 요구사항 명세서(`docs/beez-requirements-preflight.md`)에는 CTX-01~04만 있고, Notion 업무 분담안에도 ID와 "개인 맥락" 라벨만 있다. 그래서 C14의 해석으로 판단했고, 원문을 확인하면 4.4절을 보완한다.

관련 확정 사항 (재론하지 않음):

- 개인 기록은 명시적 제출, 수정은 새 리비전, 동시 수정 시 409, `kind=DECISION`은 승인 설계가 아니다 ([01 아키텍처](01-system-architecture.md) 컨텍스트 행, ERD `context_record`).
- 남의 PRIVATE 기록 조회는 403이 아니라 404이고, 검색 결과·건수에도 드러내지 않는다 ([05](05-build-order-and-access-policy.md), [06](06-project-access.md)).
- 감사 기록에는 인증정보·개인 대화 원문을 넣지 않는다 (MCP-09). MCP-01 감사에는 `request` 본문을 남기지 않는다 (#110 감사 기준안).
- 물리 삭제 없음, 기록 리비전은 트리거로 UPDATE 차단 (ERD 공통 규칙, `trg_context_record_immutable`).
- 공유 기록·개인 기록은 MCP-01 패킷에 넣지 않는다 (#110 2절 표).

## 2. POL-01 컨텍스트 분류와 근거 우선순위

[지식 그래프 재검토안](development-context-knowledge-graph-review-S15P31A108-110.md) 3.1절의 권위 수준을 그대로 쓴다. 새 분류를 만들지 않는다. 공통 문서화는 C1.

| 순위 | 분류 | 해당 데이터 | 컨텍스트에서의 취급 |
| --- | --- | --- | --- |
| A | 승인 기준 | 현재 기준(`project.current_baseline_id`)의 설계 항목 버전·문서 버전 | 개발 판단의 근거 |
| B | 명시 관계 | 확정 조건을 확인한 `EXPLICIT` 의존, 계획 참조, 작업 의존 | 탐색 경로. 관계 자체가 설계 내용은 아님 |
| C | 작업 상태 | 작업·검증·변경 제안 상태 | 현재 상황 정보 |
| D | 공유 기록 | `context_record` `SHARED` | 동료가 남긴 참고 정보 |
| E | 추론·AI 후보 | 규칙 영향 후보, `AI_CANDIDATE`, AI 영향 후보, 비비 답변 | 출처·방법을 붙인 후보 |
| 제외 | — | 타인의 PRIVATE, 다른 프로젝트, 미승인 초안 | 결과·요약·건수에 노출하지 않음 |

**충돌 규칙 (박상은 판단 · C2 확인 요청):**

1. 하위 순위 근거는 상위 순위 근거를 덮어쓰지 않는다. 예: `DECISION` 기록이 "응답 필드를 `userId`로 바꾸기로 함"이라고 해도 승인된 API가 `memberId`면 승인 API가 기준이다.
2. 충돌을 발견하면 어느 쪽이 맞는지 AI가 정하지 않는다. 충돌을 다루는 경로는 근거가 어디서 왔는지에 따라 나뉜다 (POL-05, BEE-04).
   - **승인 설계끼리 또는 승인 설계 안의 빈칸:** MCP-01이 패킷 입력(A·B·C) 안에서 찾아 `unresolved`로 반환한다.
   - **공유 기록(D)과 승인 설계:** 공유 기록은 MCP-01 입력이 아니다 (#110 2절 표, X7). MCP-01은 이 충돌을 찾지 않고 `unresolved`에도 넣지 않는다. 에이전트가 `find_context`·`read_context`로 기록을 따로 읽었을 때 승인 설계를 기준으로 삼고, 기록은 "공유 판단, 승인 설계 아님"으로 다룬다. 필요하면 `propose_design_change`(MCP-04)로 변경을 제안한다. 비비(#135)가 두 근거를 함께 찾았다면 답변에 두 출처를 나란히 보이고 "검토 필요"로 표시한다.
   - 공유 기록을 패킷에 넣어 MCP-01이 직접 충돌을 판정하게 하려면 패킷 범위 변경이 필요하다. MVP에서는 하지 않고 확장 X7로 둔다.
3. 같은 순위끼리는 최신 리비전·최신 기준을 우선하되, 과거 근거는 "과거 버전"으로 표시해 남긴다 (`is_latest_revision`, `references_current`). 현재 근거로는 `is_latest_revision=true`인 리비전만 쓴다. 이 값의 판정 기준은 2.1절을 따른다.
4. 요약에도 문서 ID·버전·항목 위치를 보존한다. 출처를 잃은 요약은 근거로 쓰지 않는다 (POL-01 원문).

### 2.1 기록 리비전의 최신 판정

`visibility`는 리비전마다 정해지므로 한 기록 체인 안에 SHARED와 PRIVATE 리비전이 섞일 수 있다. 현재 구현(`ContextLookup.superseded`)은 **보는 사람에게 보이는 후속 리비전이 있을 때만** 이전 리비전을 대체된 것으로 본다. 그래서 `SHARED rev1 → PRIVATE rev2 → SHARED rev3`이면 다른 멤버에게 rev1(후속 rev2가 안 보임)과 rev3이 모두 `is_latest_revision=true`로 나온다. 같은 판단의 오래된 판과 새 판이 둘 다 현재 근거로 쓰일 수 있다.

**박상은 판단 · C3 확인 요청:**

| 규칙 | 내용 |
| --- | --- |
| R1 최신 판정 | 최신 리비전은 기록 체인(`root_id`)에서 후속 리비전이 없는 단 하나의 리비전이다. 후속 리비전의 `visibility`와 보는 사람의 권한은 따지지 않는다 |
| R2 노출 | 노출 여부는 지금처럼 리비전별 `visibility`로 정한다. R1 때문에 숨겨진 리비전의 내용이 드러나지는 않는다 |
| R3 근거 사용 | 컨텍스트·비비·검증에서 현재 근거로는 `is_latest_revision=true`만 쓴다. 보이는 리비전이 모두 `false`인 체인(최신 리비전이 PRIVATE)은 "최신 판 비공개"로 보고 현재 근거로 쓰지 않는다 |
| R4 체인 하나에 최신 하나 | 어떤 보는 사람에게도 한 체인에서 `is_latest_revision=true`는 최대 하나다 |

**대가:** R1을 적용하면 다른 멤버는 "보이는 리비전이 최신이 아니다"라는 사실로 비공개 후속 판이 있다는 것을 알 수 있다. 내용 노출은 아니며, 이미 `root_id`·`revision_no`로 드러나는 수준(C10)과 같다. 오래된 판이 현재 근거로 쓰이는 문제보다 작다고 판단한다.

## 3. POL-02 조회 수준

**박상은 판단 · C4 확인 요청: L0/L1/L2를 두지 않고 summary/detail 두 수준만 둔다.** 기존 도구 구분에 그대로 대응시켜 새 파라미터를 추가하지 않는다.

| 대상 | summary | detail |
| --- | --- | --- |
| 공유 기록 | `find_context` 목록의 `ContextRecordSummary` (요약·종류·작성자·리비전·최신 여부·참조 현재성) | `read_context(RECORD)`의 `ContextRecord` (상세·참조 버전·당시 계획·근거 패킷 추가) |
| 컨텍스트 패킷 | MCP-01 응답 자체가 작업 하나에 필요한 범위. 별도 요약 수준 없음 | `read_context(PACKET)` |
| 개인 원문 대화 | 제공하지 않음 | 제공하지 않음 |

- 두 수준 모두 출처(문서·버전·위치 또는 작성자·리비전)와 유효성(`is_latest_revision`, `references_current`)을 포함한다. 현재 스키마가 이미 충족한다.
- 길이 상한: `summary` 500자, `detail` 10,000자. `request`의 2,000 코드 포인트 상한(#110 기준안)과 같은 방식으로 초과 시 400 `validation_failed`, 잘라 저장하지 않는다.
- MCP-01 응답 크기 상한·잘림 처리는 #132에서 정한다. 이 문서는 "잘렸으면 잘린 사실과 전체 조회 경로를 표시한다"는 원칙만 둔다.

이 대응으로 #132가 기다리던 POL-02 결정은 풀린다. #132는 `summary`/`detail`을 별도 필드로 만들지 않고 위 대응을 따른다. C4에서 다른 의견이 나오면 #132에 함께 반영한다.

## 7. 확인 이후 처리

- **동의:** 8절 표에 확인자·날짜를 적고 상태를 "확정"으로 바꾼다.
- **수정:** 수정안을 반영하고 같은 사람에게 다시 확인을 요청한다.

## 9. 발견한 불일치

담당 문서·코드라 이 문서에서는 고치지 않는다. 확인 요청 항목의 결과에 따라 담당자가 반영한다.

1. **공유 철회가 되지 않는다 (C3·C13).** `visibility`는 리비전마다 정해진다. SHARED rev1 뒤에 PRIVATE rev2를 추가하면, 다른 멤버에게는 rev2가 보이지 않으므로 `ContextLookup.superseded`가 rev1을 대체되지 않은 것으로 계산해 `is_latest_revision=true`로 보여준다. 작성자는 공유를 거둔 줄 알지만 동료에게는 rev1이 최신으로 남는다 (V7). 같은 이유로 `SHARED → PRIVATE → SHARED`이면 rev1과 rev3이 모두 최신으로 보인다 (V8).
2. **PRIVATE 첫 리비전의 존재가 드러난다 (C10).** PRIVATE rev1 → SHARED rev2이면 다른 멤버는 rev2의 `root_id`(=rev1 ID)와 `revision_no=2`로 비공개 이전 판이 있다는 사실을 알 수 있다. 내용 노출은 아니다.
3. **`find_context`가 이전 리비전도 반환한다 (C11).** 같은 기록의 여러 리비전이 검색 결과에 함께 나온다. `is_latest_revision`으로 구분은 되지만 기본값이 정해지지 않았다 (Q10 "PRIVATE·리비전·패킷 검색").
4. **MCP-05·07 이름과 PRIVATE (C12).** 도구명은 "공유 작업 기록"인데 PRIVATE 저장을 허용한다.
