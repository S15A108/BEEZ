# 회의 결정 → 문서 수정 요청 변환 (S15P31A108-138)

상태: 담당자 합의 전 제안. `prepare_meeting_revision`은 내부 함수이며 HTTP 경로,
권한 검사, 결정 확정, 저장·승인·발행을 제공하지 않는다. 호출자는 같은 프로젝트의
회의·문서 권한, 확인된 결정 및 근거 관계, 현재 승인 버전을 확인하고 사용 직전
다시 확인한다. 입력 내 ID 일치 검사는 실제 DB 소속이나 확인 여부를 증명하지 않는다.

## 현재 회의 정리와의 차이

[MTG-A11의 MeetingSummary](../api/00-common.md#schema-meetingsummary)는 정리 ID와
`decisions[{text, decided_by_member_id?}]`를 제공한다. 각 결정의 ID와 결정별
`evidence_entry_ids`는 제공하지 않으므로 이 결과를 아래 입력에 그대로 넣을 수 없다.
`document_changes[].evidence_entry_ids`는 **문서 변경**의 근거이지 특정 결정의
근거가 아니다. 어느 결정에 연결할지 자동 복사하거나 텍스트 유사도로 추론하지 않는다.

[MTG-A13](../api/01-backend-rest.md#mtg-a13)은 현재 AI-A06을 호출하지 않고
정리의 `document_changes[].after`로 변경 제안을 만든다. 아래 137·138·191 재사용은
별도 제안이며, 이 문서나 함수는 기존 흐름을 변경하지 않는다. 재사용 여부와 호출
시점은 BE 및 191 담당자와 합의하고 API 명세에 반영한 뒤 구현해야 한다.

## 결정 식별과 근거 확인 제안 — BE·FE 선행 작업

다음은 연동 전 합의할 **제안**이며 현재 제공되는 MTG-A11 필드나 구현 완료된
기능이 아니다.

1. **BE — 정리 스냅샷 고정:** 프로젝트와 회의에 속하는 저장된 `meeting_summary.id`를
   고르고 그 `decisions` 배열 순서를 보존한다. 예를 들어 0부터 센 결정 순번과 정리
   ID로 `summary:951:decision:0`을 만들 수 있다. 이는 해당 불변 정리 안에서만 쓰는
   식별자이며 발언 ID나 영구적인 결정 DB ID가 아니다. 정리 ID는 SUMMARY 발언의
   `entry.id`가 아니라 `MeetingSummary.id`다. 수정 요청으로 새 정리가 생기면
   같은 순번·문구라도 새 정리의 다른 식별자를 사용한다.
2. **FE — 사용자 확인:** 사용자에게 정리 스냅샷의 각 결정과 정리 시점까지의 같은
   회의 발언을 보여 주고, 결정별 근거 발언을 명시적으로 선택·확인받는다. 확인하지 않은 결정이나
   근거 없는 결정을 확인된 것으로 표시하거나 다른 문서 변경에서 채우지 않는다.
3. **BE — 연결 검증과 보존:** 선택된 정리 ID·결정 순번·당시 문구·확인된 발언 ID와
   확인 주체를 함께 보존한다. 각 결정과 발언이 선택된 정리 및 같은 프로젝트·회의에
   속하는지, 발언이 정리 시점의 확인 범위에 속하는지, 사용자에게 확인 권한이 있는지
   서버에서 검증한 뒤 `{id, text, evidence_entry_ids}`를 만든다. 연결이 없거나
   검증할 수 없는 결정이 하나라도 요청에 포함되면 이 변환 호출을 보류하고 사용자에게
   확인이 필요함을 알린다. 오류 코드와 저장 방식은 191·BE 계약 합의 대상이다.

현재 정리는 `through_entry_id`까지만 다뤘다는 경계를 저장하지만, 실제 AI 입력은
최근 발언 개수·요청 크기 한도로 일부만 선택할 수 있고 이전 정리가 따로 포함될 수도
있다. 따라서 `through_entry_id` 이내라는 사실만으로 AI가 그 발언을 실제로 보았다고
증명할 수 없다. 위 연결은 **사용자가 확인한 근거**로 표시한다. 191에서 실제 AI 입력에
포함된 발언으로만 제한해야 한다면, BE가 정리별로 실제 전달한 발언 ID와 입력 스냅샷을
추가로 보존·검증하는 선행 작업이 필요하다. 허용 범위는 BE·191과 합의한다.

현재 함수와 191의 `meeting` 구조에는 별도 `summary_id` 필드가 없고 ID 형식이나
사용자 확인 여부를 검증하지 않는다. 따라서 BE는 위 출처와 확인 상태를 별도로
안전하게 유지·대조해야 한다. 138·191은 동일한 결정 문구의 중복도 거절하므로,
중복이 있는 정리는 임의로 합치지 않고 사용자 확인과 계약 협의가 필요하다.

## 변경 시 재확인 제안

BE는 AI 호출 전과 결과를 저장·사용하기 직전에 정리 ID가 회의의 최신 정리인지,
정리 이후 입력 범위에 새 회의 기록이 생겼는지, 결정 문구와 확인된 근거 연결 및
호출자 권한이 그대로인지 확인한다. 대상 문서가 같은 프로젝트에 속하고 승인 문서
버전·기준·원문 해시·선택 블록도 확인 당시와 같은지 다시 확인한다. 저장이나 후속
사용과 재확인 사이에 값이 바뀌지 않도록 BE가 트랜잭션 또는 동등한 동시성 제어를
맡는다. 이 확인은 현재 AI 함수가 제공하지 않는다.

새 정리·정리 이후 기록·근거 연결 또는 문서 기준 변경, 권한 철회 등이 확인되면
진행 중인 결과를 현재 근거로 사용하지 않고 보류한다. FE는 최신 정리와 발언을 다시
불러오고 결정·근거를 사용자에게 재확인받는다. 이전 순번이나 같은 문구만으로 기존
연결을 새 정리에 자동 이월하지 않는다. 실제 충돌 응답과 기존 `summary_outdated`
재사용 여부는 BE·191 협의 후 확정한다.

## 입력과 변환

- `project_id`, `meeting_id`, `document_id`, `document_version_id`: 서버가 확인한 식별자.
- `source`: 137의 SourceInput 전체. 문서 버전·프로젝트가 위 값과 일치하고, 정규화된
  원문과 text_hash·파서 프로필이 유효해야 한다. document_id와 버전의 실제 관계는 BE 책임이다.
- `entries`: 같은 회의의 `{id, meeting_id}` 목록. `decisions`는 확인된
  `{id, text, evidence_entry_ids}` 목록으로, 근거는 해당 입력의 발언 ID여야 한다.
  결정·발언 ID와 결정 문구의 중복은 거절한다. ID 출처, 결정 확정·근거 확인 및
  정리 최신성은 입력 제공자가 보장한다.
- `selected_block_ids`: 같은 스냅샷의 파서 블록 ID 1~30개. 빈 목록, 중복 또는 다른
  스냅샷의 ID는 거절한다. 검색 청크나 설계 항목 ID를 대신 사용하지 않는다.
- `instruction`, 선택 `related_proposals`, `request_key`: 137 요청과 같은 의미.
  프로젝트별 권한과 제안의 관련성 확인은 호출자 책임이다.

아래는 형태 예시이며 `source`의 필수 필드는 137 계약을 따른다.

```json
{
  "project_id": "1", "meeting_id": "3", "document_id": "4",
  "document_version_id": "2", "source": {"...": "137 SourceInput 전체"},
  "entries": [{"id": "5", "meeting_id": "3"}],
  "decisions": [{"id": "summary:951:decision:0", "text": "팀장만 삭제", "evidence_entry_ids": ["5"]}],
  "selected_block_ids": ["해당 스냅샷의 블록 ID"],
  "instruction": "삭제 권한 수정", "related_proposals": [], "request_key": "req-138"
}
```

반환값의 `meeting`은 프로젝트·회의·문서·버전·발언·결정 관계를 보존한다.
`request`는 `source`, `expected_document_version_id`, `selected_block_ids`,
`instruction`, `agreements`(결정의 text 순서 그대로), `related_proposals`,
`request_key`를 담는다. 191 `connect_meeting_revision`에는 각각 `meeting`과
`request`를 `context`와 `prepared_request`로 전달하는 방안을 제안한다.
근거 텍스트의 유사도로 발언 ID를 추론하거나 변경 항목에 자동 연결하지 않는다.

## 오류와 결과

변환 중 검증 실패는 `ValueError` 계열(Pydantic ValidationError 포함) 또는
`SourceParsingError`다. 예: 다른 회의 발언·없는 근거 ID·버전 불일치·빈 선택·
잘못된 원문 해시는 호출하지 않고 실패한다. HTTP 상태와 오류 본문은 아직 합의된
공개 계약이 없으며 호출자가 정한다. 191·137에서 발생한 모델 오류와 usage,
변경 없음 및 unresolved는 변환부가 성공 초안으로 바꾸지 않는다.

## 검증과 남은 합의

변환 테스트는 실제 정리 결정에 필요한 ID·결정별 근거가 없을 때의 보류, 문서 변경
근거 자동 복사 금지와 스냅샷별 ID 보존, 다른 회의·없는 근거·중복 결정·다른
프로젝트·다른 버전·범위 오류를 검사한다. 스냅샷 ID의 진위·최신성이나 사용자의
확인 여부는 이 테스트와 함수로 증명할 수 없다. 191 `902fee4c`와 137 `28f07e24`의
실제 함수를 격리된 검사 사본에서 가짜 모델로 연결해 선택 문단만 바뀌고 결정→발언
링크가 유지됨을 확인했다.
이는 실제 모델, 회의 DB, 권한·현재성, 저장 또는 사용자 화면 검증이 아니다.

양지훈 님과 최종 필드·오류·호출 책임 및 MTG-A11/A13의 기존 회의 정리 흐름과
공통 모듈 재사용의 관계를 합의해야 한다. 두 선행 PR은 미병합이므로 이 문서와
함수는 합의 완료나 운영 연동 완료를 주장하지 않는다.
