# #131 개발 컨텍스트 선택 시나리오와 인공 후보

## 목적과 범위

[#130 개발용 나래 문서 4종](../../ai/evaluations/data/questions.json)을 이용해 #131의 선택·의존 확장과 오류 구분을 점검할 대표 사례를 준비했다. 입력과 독립 기대값은 [시나리오 fixture](../../ai/tests/fixtures/retrieval/context-selection-131.json)에 있다. 설계 항목·관계·작업 계획 참조와 선택 결과는 이 문서를 바탕으로 **인공으로 만든 개발용 데이터**다. 해당 항목이나 관계가 실제 발행됐다는 뜻이 아니다. 원문 인용은 #130 데이터에 존재하는 문장을 사용한다. 라벨은 작성자가 만든 초안이며 독립 사람 검토가 필요하다.

fixture의 `snapshot`은 BE가 권한과 현재 기준을 확인해 전달했다고 가정한 입력이고, 각 `fake_proposal`은 선택 공급자의 모의 출력이다. 이는 실제 의미 검색·LLM 호출·BE/DB 연동, 검색 정확도 평가가 아니다. 선택 검증이 성공해도 후보의 의미적 관련성까지 입증하지 않으며, 이 자료로 운영 정확도·재현율을 주장하지 않는다.

## 대표 요청과 기대 결과

| 사례 | 입력 및 인위적 선택 | 기대 결과 |
| --- | --- | --- |
| 업로드 생성 | POST 생성 설계 `1102`와 원문 `e-post`, `e-limit`를 직접 선택 | 확정 명시 관계의 한 단계 대상 `1101`을 `DEPENDENCY`로 포함한다. 2단계인 발행 정책 `1100`, GET 목록 `1103`, 재확인 필요 관계의 `1104`는 포함하지 않는다. |
| 작업 계획 반영 | 위 요청과 현재 작업의 `1004/1104` 참조 | `1104`를 `TASK_PLAN`으로 추가한다. 확정 관계로 표시하거나 작업을 시작하지 않는다. |
| 소유자 참조 | 데이터 설계 `1104`와 원문 `e-owner`를 직접 선택 | `1104`만 `MATCHED`다. 비슷한 이름만으로 FK나 역방향 의존을 만들지 않는다. |
| 원문만 존재 | 재시도 원문 `e-retry`만 선택 | 원문 근거를 반환하고 설계 항목을 새로 만들지 않는다. |
| 보관 기간 미정 | 정상 검색 뒤 선택 0건 | `NO_MATCH`로 구분하고 기간을 추측하지 않는다. |
| 미준비·검색 실패 | 각각 `NOT_READY`, `FAILED` | 선택 공급자를 호출하지 않고 각각 `context_not_ready`, `search_failed`로 실패한다. |

`irrelevant-allowed-id-negative-example`은 **의도적인 혼입**이다. 업로드 생성 요청에서 GET 목록 항목 `1103`과 `e-get`을 선택해도 두 ID가 허용된 후보에 속하기 때문에 단순 부분집합 검사는 이를 막지 못한다. 이 사례는 관련성 검증의 한계를 드러내며 무관 후보가 자동으로 배제됐다는 근거가 아니다. 유의미한 품질 평가는 별도 정답 라벨의 독립 검토와 실제 검색·선택 결과 측정이 필요하다.

## 실행과 해석

입력 구성 시 각 시나리오의 `request`, 선택적 `task_id`·`task_design_refs`·`search_status`로 `snapshot`의 해당 필드를 덮어쓴다. `evidence_override`가 있는 경우에만 증거 목록을 교체한다. `fake_proposal`은 `SelectionProposal`로 변환해 모의 공급자가 반환한다. `expected_design_items`의 순서는 기준 후보 목록 순서이며 `expected_evidence_ids`는 공급자가 선택한 순서다. 오류 사례는 코드와 호출 횟수를 확인한다. 혼입 사례는 `expected_irrelevant_ids`가 실제 결과에 남는 것을 확인하는 음성 대조군이다.

시나리오에 쓰인 원문은 `document_paths`의 각 파일에서 직접 확인할 수 있다. 버전·프로젝트 ID와 청크 ID는 시험 식별자다. 정책·문서 원문·AI 선택을 별도 출처로 취급하며, 본 테스트의 정상 여부와 별개로 MCP-01의 실제 인증, 색인 READY, 관계 조회 및 최종 baseline 재검사는 BE 통합에서 검증해야 한다.
