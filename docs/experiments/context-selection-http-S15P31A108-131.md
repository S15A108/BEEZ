# 개발 컨텍스트 선택 내부 HTTP 초안 (#131)

**제안·비활성 상태다.** `POST /v1/development-context-selections`는 BE가 권한과 현재 승인 기준을 확인해 제공한 스냅샷에서 기존 #131 선택기를 실행한다. 이것은 BE나 MCP 연결 완료, #132 패킷 구성, 충돌의 의미 검증 또는 운영 계약 확정을 뜻하지 않는다. 요청 분석·미확정 LLM 검토는 이 경로에 연결하지 않는다.

## 운영 설정과 비용

서버의 `CONTEXT_SELECTION_ENABLED`는 기본 `false`다. 활성화에는 서버의 `GMS_KEY`, `CONTEXT_SELECTION_MIN_SIMILARITY`, `CONTEXT_SELECTION_MAX_ITEMS`, `CONTEXT_SELECTION_MAX_EVIDENCE`, `CONTEXT_SELECTION_TOTAL_TIMEOUT_SECONDS`를 모두 명시해야 한다. 누락·잘못된 값은 본문을 읽기 전에 503 `selection_not_configured`다. 임계값 범위는 -1~1, 상한은 종류별 0~200(동시 0 불가), 선택 실행 예산은 0초 초과~120초다. 이 문서는 운영 임계값이나 예산을 채택하지 않는다. 모델·임계값·상한은 요청에서 지정하지 못한다. JSON의 미허용 필드는 거부한다.

활성화 시 기존 GMS 임베딩 프로필·고정 공급자 주소와 환경 프록시/리디렉션 비허용 정책을 사용한다. 요청과 전달받은 후보를 다시 임베딩하므로 유료 호출과 지연이 생긴다. 자동 재시도는 끈다. 사용량·전송·비용 정책과 실제 검색 품질이 합의되기 전에는 운영에서 활성화하지 않는다. 테스트는 가짜 공급자만 사용한다.

전체 시간 예산은 **본문 수신·검증을 제외한 선택 실행**에 적용한다. BE의 현재 기본 read timeout 20초보다 항상 작다는 보장은 없으며, 네트워크·검증·응답 저장 시간을 포함해 담당자가 두 예산을 함께 정해야 한다. 시간 초과 시 취소 예외에서 확인 가능한 호출 usage를 보존해 504 응답에 넣는다. 클라이언트 연결 중단, 응답 유실, 프로세스 강제 종료 시 서버 응답만으로 사용량을 저장할 수 없으며 별도 영속화·상관관계 계약은 미해결이다.

## 입력·출력

`Authorization: Bearer <AI_INTERNAL_TOKEN>`이 필요하다. 인증과 서버 설정 확인이 성공해야 본문을 읽는다. `Content-Type: application/json`이며 OpenAPI에 스키마가 제공된다. 본문은 262,144바이트를 넘을 수 없고 수신 중 실제 바이트 수로 제한한다. 문서 버전 최대 1,000개, 승인 설계와 원문 근거는 각각 최대 200개, 관계 최대 1,000개, 작업 참조 최대 200개다. 이 수치는 운용 계약이 아니라 초안의 보호 상한이다.

요청은 `request_key`, `project_id`, `baseline_id`, `request`, 선택적 `task_id`, `document_version_ids`, `items`, `evidence`, `relations`, `task_design_refs`, `search_status`를 포함한다. `request_key`는 BE가 부여하는 1~128자 UTF-8 상관 식별자로 공백만 있거나 출력할 수 없는 문자(줄바꿈·NUL 등)를 포함한 값은 거부한다. 이는 공통 계약에서 아직 명시하지 않은 본 초안의 추가 제한이며 담당자 합의가 필요하다. 키는 usage에 그대로 포함되므로 요청 본문, 개인 정보, 토큰이나 비밀번호를 넣지 말고 의미 없는 식별자를 사용한다. ID와 범위, 승인 상태, 중복 및 작업 참조는 내부 `SelectionInput` 검증을 따른다. BE가 전체 수집 범위·후보 원문·관계 양 끝의 당시 버전을 검증한 단일 일관 스냅샷을 보내고, 결과 사용 직전 멤버십·기준·관계·계획 최신성을 다시 확인할 책임이 있다. 외부 문서 청크는 승인 설계 항목으로 임의 승격하지 않는다. 기존 관계 API와 이 DTO 간 버전 공급 및 일관성 계약은 별도 협의가 필요하다.

성공의 `result`는 설계 버전 ID와 선택 이유, 원문 근거 ID, 검색 상태, `NO_MATCH` 여부, 직접 선택 상한으로 제외된 후보 수를 포함한다. `usage`는 실제 시작한 임베딩 호출 기록이다. 상한 제외 수는 전달받은 후보와 임계값에 한정되며 의미적 관련성이나 전체 BE 검색 누락을 보증하지 않는다. 후보를 0개 받은 정상 검색은 모델 호출 없이 `NO_MATCH`다. 요청 원문·설계/근거 원문과 내부 `snapshot_binding`은 응답하지 않는다. 직렬화된 결과는 원래 in-process 일치 표식을 복원할 수 없다.

## 오류와 한계

- 인증 실패는 401 `invalid_internal_token`, 비활성·미설정은 503 `selection_not_configured`다.
- 잘못된 JSON·필드·범위·중복은 400 `validation_failed`, 다른 미디어 타입은 415, 바이트 초과는 413이다. 검증 전에는 선택 공급자를 호출하지 않는다.
- 미준비는 503 `context_not_ready`, 실제 검색 실패는 502 `search_failed`다. 둘 다 정상적인 `NO_MATCH`가 아니다.
- `selection_incomplete`를 포함한 선택 실패는 결과를 성공으로 바꾸지 않는다. 타임아웃은 504 `embedding_timeout`이며 확인된 호출 usage는 오류에 포함한다. 기타 오류 코드는 현재 내부 구현의 정제된 코드이며 상태/DTO의 최종 외부 계약은 아니다.
- `X-Request-Id`는 전송 추적용이다. 안전한 1~128자 영숫자·`._:-`만 반사하고, 없거나 유효하지 않으면 서버가 생성한다. 본문의 `request_key`는 별개의 BE 요청 식별자이며, 각 `usage[].request_key`는 해당 값에 호출별 고유 식별자와 배치·시도 정보를 덧붙인다. 같은 입력 키로 요청을 재시도해도 실제 호출마다 다른 usage 키가 생성되며 요청 멱등성은 보장하지 않는다. 키에 구분자가 포함될 수 있으므로 BE는 usage 키를 문자열 분할해 원래 키를 추론하지 말고 **같은 응답의 usage 목록**을 자신이 보낸 요청과 함께 저장한다. 응답을 받지 못한 경우의 사용량 복구·별도 저장 및 중복 처리 계약은 여전히 미해결이다. 원문·공급자 오류 메시지는 응답에 넣지 않는다.

직접 `EmbeddingContextSelector`를 구성하는 내부 호출자는 선택적으로 `request_key`를 지정할 수 있다. 이 값은 인스턴스에 고정되므로 논리 요청마다 새 인스턴스를 만들어야 한다. 지정하지 않는 기존 호출은 내부에서 생성한 별도 키를 사용한다. HTTP 경로는 매 요청의 입력을 검증한 뒤 해당 요청 전용 선택기를 생성한다.

이 endpoint는 내부 인증 외 프로젝트 권한이나 DB 최신성을 증명하지 않는다. BE·AI DTO, 부분 결과 허용 여부, usage 저장·중복·취소, 발췌 복원 및 모델/임계값은 담당자와 합의한 후 실제 데이터 통합과 독립 품질 평가를 해야 한다.
